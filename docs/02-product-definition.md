# 02 · 产品定义(Product Definition)

> 本篇定义 SayDo 的用户、场景、核心交互循环与产品边界。上一篇:[01 · 背景与问题](01-vision-and-problem.md);技术实现见 [03 · 架构](03-architecture.md) 与 [04 · 关键机制](04-key-mechanisms.md)。

## 1. 目标用户与三个基准场景

三个场景由窄到宽,构成同一个工具的能力光谱(原始需求基线与逐条 checklist 见 `../history/scenarios/`):

| # | 场景 | 主角 | 最终产出 | 优先级 |
|---|---|---|---|---|
| S1 | 工程师直接口述需求,派 agent 开发 | 工程师(懂技术) | 代码改动 / PR | **P0 主线** |
| S2 | 非技术负责人捋思路 → 先生成完整开工文档体系 → 再实施 | CEO / 产品负责人 | 文档体系 + 后续代码 | P3 |
| S3 | 非开发项目(调研 / 写文章·论文 / 营销 / 设计 / 谈客户准备…) | 任意角色 | 报告 / 文章 / 方案 / 行动计划 | P2(writing 窄版已提前,§5.0) |

S2/S3 的存在决定了一个关键设计:**worktree、verify 测试、PR 只是 `coding` 类型的具体实现,不是全局假设**;产物模型与验收标准按项目类型切换(§5)。

## 2. 核心交互循环(业务全景)

**你只管对着它说话** → AI 先把项目**研究透并沉淀成持久记忆**,同时**采访式**把需求问清 → 每轮自省"够不够开始",够了**主动给决策包**(成果预览 + 计划 + Demo)请你拍板 → 你说"开工" → 它**派本地 agent 后台干活**,你可以走开 → 执行和检查跑完等你验收、或卡住需要你时,它**主动叫你** → 你验收/改 → 合并交活 → 全程知识与产物**持久化、可召回续用**。

```
聊(采访+自研)→ 就绪自省 → 决策包 → 人拍板 → 后台执行 → 回叫 → 验收 → 沉淀
      ▲__________________________________________________________________|
                        (知识与产物滚动积累,越用越懂你和项目)
```

分步说明:

1. **开场:选定项目**。会话锚定一个项目是起点。**控制台首页(Dashboard)即主入口,提供两大动作:「开始新对话」与「选择已有项目继续」**;新对话在**用户开口时**创建 draft 项目(点开麦不建,防空 draft 垃圾;占位名,类型与名字由 AI 在对话中识别回填,**不出现建项表单**),奠基完成/首个决策包确认后转正。无锚定项目的通用归属问题每个 live session 最多播一次，daemon 在 TTS 前先持久化 `reserved`，enqueue 成功才落 `asked`，失败落 `enqueue_failed` 并允许重试；重启遇到孤立 `reserved` 时为守住“不重复问”而保守视为已问，只有明确 `enqueue_failed` 才重新开放；输出闸拦截重复，不能只靠 Brain 提示词自觉。归属状态显式分为 `unasked_draft`、`asked_unresolved`、`anchored`，已锚定会话不再问归属、索路或签发 draft 归属候选。用户后续继续描述需求时按新事情承接，点名已有项目时走下述安全出口。若聊着发现其实是已有项目的事,AI **提议**重新锚定，但 P0 只有两种有机械身份的入口可以改库：用户在受信 console 选择已有项目，或未锚定会话中用户在当前原话里用单一、正向归属表达说出本地路径后确认。合法显式路径轮由 daemon 在进入 Brain 前机械路由；exact 已登记路径直接进入封闭确认，新路径缺类型才交给 Brain 识别；否定、比较、多个路径及“给某路径加功能”都不构成归属表达。只说项目名时 AI 引导这两个出口，`resolveProject` 只接受项目名本身或“继续/接着/回到/切到”等归属意图，对含路径、需求载荷、无匹配或多匹配 fail-closed，不拿模糊名称 + 泛化肯定自动挂靠(锚错即跨项目污染;draft 已产生的转写/候选记忆按 candidate 写路径并入目标项目或随 draft 废弃)。用户点名的本地工作区尚未登记时,daemon 只从**当前用户原话里的唯一路径字面量**解析并只读核验目录,机械复述“这个本地项目”与类型请求确认;封闭肯定后才让当前 draft 采用该工作区,若 canonical path 已对应现役项目则改为并回该项目。否认、歧义、路径不存在或路径不是本轮用户亲述均零写入,绝不由 Brain 编造路径后自动挂靠。全新项目触发**奠基**(先研究透才开聊,显示"学习中"状态);已有项目做轻量预热(加载知识库 + 增量刷新)。项目工作区 P0 选**本地文件夹**(云端 repo 后续支持,落地时也是 clone 到本地);非代码项目默认用系统管理文件夹,不被"先选文件夹"拦住;**coding 项目的工作区定序**:AI 识别为 coding 且需奠基时,口头请求 + 屏幕弹目录选择器,选定前对话可继续、奠基挂起。
2. **对话:AI 主导采访 + 主动备料**。AI 不做"记录员",而是像播客主持人采访嘉宾:带着对项目的理解主动提问,一次一问、选择题优先;同时在后台持续准备知识(哪怕你没提问)。需求清晰就一两句确认,模糊就多问几轮,但不没完没了。
3. **就绪决断:AI 判断火候**。每轮回答结束,AI 自省"知识够不够 + 需求清不清",两维都够才收敛;不够就定向补缺口(知识不够 → 主动学习;需求不够 → 定向追问),不发散到无关话题。
4. **决策包:看着东西拍板**。就绪时 AI 主动端出三件套——**成果预览**(做完你会得到什么)、**实施计划**(每步显式标注 **AI 执行 vs 需要人配合**)、**Demo**(可能的话,一个轻量 HTML 预览"最终长什么样";非 UI 类用报告样章 / 方案一页纸代替)——然后明确问:"**要不要现在就开始?一口气跑完,还是每步问你?**"(拍板时同时选执行模式:**直达验收 / 逐步确认**,见 [04 · 关键机制](04-key-mechanisms.md) §5.4;**用户不置可否时按逐步确认执行——即使项目默认是直达验收,因为预授权清单未经念读确认不生效**;AI 可按任务风险给推荐,但推荐不占预选位、确认句保持中性二选一;高危动作的门槛不随档位降低。)
5. **执行:异步、隔离、有熔断**。确认后任务进入后台执行(coding 类型在独立 git worktree),语音会话挂起(零成本),人走开。执行有预算/时长/回合熔断,不会无人值守烧钱。
6. **回叫:值得打扰才叫**。优先级:卡住等人 > 失败 > 待审批 > 完成(进度默认不打扰),按升级链叫人(语音回叫 → 桌面通知 → 手机推送 → 电话),有免打扰窗口和输出仲裁(开会时不插话)。
7. **验收与沉淀**:回叫口径是"等你验收"而非"做完了"(合并/交付永远人拍板);口播摘要 → 细节转屏幕(按验收标准组织的证据视图:diff/测试/决策/未验证项)→ 改需求可中途插话(**送达语义取决于执行后端**:支持 live steer 的即时注入,不支持的会终止本轮再续跑,AI 会如实说明,见 03 §5)→ 通过后合并/交付;需求、决策、调研资料全部落产物库,重要的提炼进项目知识底座。

## 3. 交互设计要点

- **双向语音,不是"转文字输入框"**:流式、可打断(barge-in)、亚秒首响;判定标准为 P50 ≤ 1.5s / P90 ≤ 2.5s 说完到出声。
- **显式轮次边界作 VAD 兜底**:中文口语 + 英文标识符混说时 VAD 易误断,控制台提供"说完了"(Done speaking)按钮/热键与"重听上一问"(Listen again),嘈杂环境或长思考时切显式模式(同行产品 InfiniSynapse 实证有效)。
- **透明的"学习中"状态**:奠基/补料的等待必须可理解——说清在学什么、进度、还要多久,让用户感到"AI 现在懂得更多了",而不是转圈干等。`learning` 是一等会话状态。
- **口播短、细节上屏**:三层摘要(一句话 / 150 字走读 / 决策清单);diff、日志、长文档永远走屏幕。
- **注意力预算原则(横切)**:每多占用一分人或模型的注意力,都要有明确回报,否则砍掉——回叫要值得打扰、口播要短、采访不啰嗦、模型上下文只装决策相关内容。
- **失败可见性(横切)**:任何环节失败必须有真实反馈 + 留痕,绝不静默吞没。语音场景更甚——失败要"说出来"。(来自 OctoDesk Work Steward 的一手教训。)
- **不承诺时长**:模型无法可靠预估 agent 任务耗时,话术是"做完我叫你",不说"大概半小时"。

## 4. 三条对话路径

用户进入对话有三条路径,差异在于上下文如何准备与拼接(记忆架构详见 [04 · 关键机制](04-key-mechanisms.md) §1):

| 路径 | 主入口到达方式 | 系统动作 |
|---|---|---|
| **全新项目** | Dashboard「开始新对话」→ draft 项目 | 触发**项目奠基**:阻塞式深度研究,建立持久的项目知识底座后才实质开聊("先备后答") |
| **已有项目 · 新对话** | Dashboard 项目卡「继续对话」/ 侧栏项目切换器 | 加载知识底座 + 按话题增量刷新(代码变更走 `git diff` 增量) |
| **续接对话** | Dashboard 项目卡"最近会话"直达 / 对话页会话历史 | 加载该会话完整历史 + 知识底座 + 相关积累产物,无缝续聊;结束时沉淀回知识库 |

**奠基有无,就是"有价值的持续对话"与"ChatGPT 新窗口"的分界。**

## 5. 项目类型模板

预制多套类型模板(开发 / 调研 / 写作 / 营销 / 规划 / 通用——通用含设计方案、谈大客户准备等)。模板是"**类/框架**",不是固定 workflow:作用是让 AI 开场识别"这是哪一类事",从而套用该类型的思考框架,但不固化"一步步怎么做"。

每个模板定义四样东西:

| 要素 | 说明 |
|---|---|
| 识别线索 | 从用户开场判断属于哪一类 |
| **就绪清单** | 该类型"可以开始"前必须澄清/准备到什么程度——**每类不同**,是就绪自省的判定依据 |
| Demo 形态 | 用什么预览"最终会得到什么" |
| 产出物与验收 | 该类型的交付形态与验收方式 |

示例:

| 类型 | 就绪清单要点 | Demo 形态 | 产出 / 验收 |
|---|---|---|---|
| `coding` | 目标 / 可验证的验收标准 / 涉及范围 / 约束 / 代码库关键部分已理解 | 可点的 HTML 原型 | 代码 + PR / verify(测试/构建/lint)+ 人验收 |
| `research` | 调研问题 / 范围与深度 / 交付形式 / 信息源可及 | 报告大纲 + 一节样章 | 报告 + 资料库 / 内容评审 |
| `writing` | 核心论点(用户亲口给出并确认)/ 目标读者与发表场景 / 文体·篇幅 / 结构大纲 / 论点—素材覆盖(经验或已验证引用)/ 风格参照可及(既往文章或口头描述) | 提纲(论点树)+ 一段风格样文 | 文章稿(md 源稿,按需导出 docx/LaTeX)+ 参考文献 / 逐节内容评审 + 口吻确认 |
| `marketing` | 目标与成功指标 / 受众 / 渠道 / 预算 / 调性 | 方案一页纸 + 样例素材 | 方案 + 内容 / 目标契合评审 |
| `planning` | 目标 / 范围 / 相关方 / 成功标准 | 文档体系目录 + 关键页样张 | PRD/架构/任务分解/里程碑 / 可开工评审 |

**为什么就绪判定必须类型化**:"上下文够不够、能不能开始"不是通用判断——开发缺验收标准不能开工,调研缺信息源没法查,写作缺核心论点成不了文,营销缺受众没法定调。先识别类型,才能拿对应清单做就绪决断。

**清单的机械承载(A3-armed 2026-07-28)**:上表 key 词表以 contracts `READINESS_CHECKLISTS` 为**唯一单源**(09 §13 readinessSkeleton 与 Brain instructions 采访段同源生成,禁手写复制品);每项带 critical 标志与 axis(requirement/knowledge)——**critical=阻塞(未确认覆盖则机械出不了包),非 critical=建议(缺口可播报,不阻塞组包)**,门语义由 09 §13 `isReadinessBlocking` 承载;覆盖成立 = 用户亲口给出 + 复述确认升格(candidate→confirmed,09 §13 covered 块——Brain 单方记账不算覆盖);另有 `pending` 最小清单(type_intent + rough_goal)承载未定型项目的首提案就绪(09 §13)。

**三个正交档位,防"小事重流程"也防"快=失控"**:① **对话车道**(Quick 一两句确认直接干 / Guided 标准采访 / Explore 开放脑暴,用户一句话可切);② **执行模式**(直达验收 / 逐步确认,拍板时选,04 §5.4;Quick 车道下无 S2 预授权需求时**不问模式**、直接用项目默认档——修 typo 不该听一遍"一口气还是每步问");③ **治理深度**(由动作效果风险决定,S0–S3)。守门句:用户可以把对话调快、把确认调稀,**但不能把任何动作的风险等级或 S3 门槛调低**。

## 5.0 写作类型(`writing`):正式文章 / 论文

典型:行业长文、专栏、技术博客、学术 paper。全套主闭环(奠基 → 采访 + 自研 → 就绪 → 决策包 → 拍板 → 后台成文 → 回叫 → 验收 → 合并回主分支 → 沉淀;合并段按类型执行合同,writing 已复用 worktree+S3 卡合并链,04 §6 / 09 §6.1a)与执行模式两档原样复用——用户把想法聊透,聊到差不多说"开始写"(或 AI 判断就绪主动提议),后台成稿等验收;直达验收 = 一口气成稿,逐步确认 = 每节停靠过目。修订走通用返工链(验收提意见 → 返工再验),多轮打磨是该类型常态而非异常。识别为学术 paper 时,就绪清单追加 paper 子档项(相关工作与文献缺口 / 引用规范与投稿模板 / 署名与 AI 使用披露口径),普通文章不强塞。**分期**:窄版合同已落(R-A 2026-07-26,09 §6.1a writing 执行合同 + §3.3 合并链复用 + `enabled_project_types` 开值随 W4,2026-07-27 回收缺省开值(Codex 21 A4);owner 拍板 **worktree 交付**——OctoBlog 在隔离 worktree 写稿、逐节内容评审、S3 卡合并回主分支);引用级引证合同、归属合同(user_authored/user_quoted)、parentProjectId lineage、对外发布集成全量仍 P2(R-C)。

**与 `research` 的分界**:research 交付"我搞清楚了什么"(对内报告 + 资料库),writing 交付"向特定读者论证一个观点"(对外成文)——调研在前者是目的,在后者只是补证据的手段。聊着聊着从调研走向成文是常见演化:AI 识别到产出目标变为"一篇对外文章"时,提议按写作清单补就绪(核心论点/读者/文体),已有调研产物经产物库召回复用,不推倒重聊(演化落地语义 owner 2026-07-25 已拍板:**`Project.type` 不可变,跨型演化 = 派生子项目**——新项目挂 `parentProjectId`,母项目产物以带 provenance 的证据身份进入子项目就绪评估,母项目及其决策包不改型、不作废;字段与 lineage/旧产物重验细则 P2 随 writing 执行器接入时落 09)。

三条特有纪律(治理哲学挂靠已有机制;引用级合同为 P2 设计项):

1. **实质内容主源是用户之口**:这是实质观点必须靠采访挖出来的最典型类型——AI 可以且应该代查(相关工作、数据、候选证据),但不能代想。采访目标从"澄清要求"扩展为"挖出内容":核心论点、独特经验、反直觉判断必须来自用户(`SourceRef.kind="user_utterance"` 锚 `TranscriptTurn.turnId` 溯源,09 §1/§4),AI 只补结构与外部证据,防"AI 代写空洞文"。就绪自省(04 §2.2)在此类型下:需求明确度 = 文章定义清楚(读者/文体/篇幅/结构),知识充分度 = 素材挖够 + 证据查够;"核心论点已由用户确认"是 critical 项——仅有 agent_output 支持的核心主张不构成有效支持(09 §4.1 critical-support 资格),与 04 §1.4"第三方内容不能定义用户偏好"同为 provenance 纪律的投影。归属合同细则(user_authored 与 user_quoted 之分、speaker=user 且 heard=true 才计为用户陈述、用户采纳 AI 候选论点只改采用状态而非回写为用户原创)P2 随 09 定契约,当前显式留白。
2. **引用完整性**:幻觉引用 = critical 失败,这是原则;落地上,就绪期"论点—素材覆盖"清单项的引证抽查直接复用 09 §4.1(SourceSnapshot/VerifiedExcerpt 捕获 + integrity/freshness/quoteMatch 机械验证);**执行/验收期对稿内引用逐条验证的合同**(引用条目实体、消费面、遗忘闭环挂钩、语义判断预算)P2 接入时基于 09 §4.1 扩展设计,当前显式留白。引用元数据随稿沉淀产物库。
3. **风格与发表治理**:风格样文是决策包必备件,经用户确认后才作口吻基准(AI 自写样文不能自证"像用户"),"口吻像不像我"属验收标准;写稿动作按 04 §5 效果分级(项目工作区内写文件 = S1),**对外发表 / 投稿 / 发给编辑是出圈动作**(对外发消息 = S3 屏幕强认证),不因"只是发篇文章"降级。

## 5.1 用户可配置性(全局默认 + 项目覆盖)

让不同成本、不同倾向的用户都能用,三处模型都开放配置:

| 配置 | 内容 | 归属 |
|---|---|---|
| **对话模型** | 语音对话的低延迟档(要快) | 全局默认,项目可覆盖(P1) |
| **思考模型** | 决策包/任务卡起草、奠基提炼的深推理档(要好) | 同上 |
| **开发模型** | 派发执行用哪个 agent(Claude/Codex/Cursor)及其模型(要省或要强) | 全局默认偏好;项目可覆盖(如某 repo 只允许有 OS 沙箱的 Codex) |

另有:**成本倾向预设**(经济/均衡/品质,一键切三处模型组合,P1)、执行模式项目级默认(出厂=逐步确认)、预算上限、免打扰窗口(全局);verify 白名单、setup 命令、工作区(项目级)。**一条护栏**:就绪评估器必须与对话/思考模型**不同家族**(防相关错误链,04 §2.3)——配置页在同家族时警示并默认拦截,不让护栏在设置里悄悄失效。

## 6. 非技术用户适配(场景 2/3)

- 验收基于**文档/业务**而非 diff/测试——回叫时讲"做出来的东西对不对",不讲"测试过没过";看细节走渲染结果/Demo,不强迫看代码。
- 审批用**业务语言**复述("这个改动会多花两天,继续吗",而不是"要装 lodash 吗")。
- 规划类项目走"深度采访 → 生成文档体系 → 屏幕协同审阅(多轮修订、版本留痕)→ 批准 → 拆解为任务批量派单 → 实施"的阶段流水。

## 7. 部署形态(产品视角)

**沟通天然是移动的,执行天然是固定的。** 手机只做**沟通面**(语音 I/O、看 Demo/diff、拍板、审批),重活(奠基、记忆、agent 执行)全在桌面/服务端执行面;手机断连不影响后端执行——这是"隔夜交活"成立的前提。

| 拓扑 | 沟通面 | 执行面 | 分期 |
|---|---|---|---|
| T1 单机本地 | 桌面浏览器控制台 | 同机 | P0 |
| T2 移动沟通 + 桌面执行 | 手机(原生外壳) | 家里/公司的桌面(macOS 或 Windows;设计 ADR-004;工程对齐进行中,未对外宣布支持) | P1(主形态) |
| T3 移动沟通 + 服务端执行 | 手机 | 云端/自托管服务器 | P2 / 愿景 |

移动端回叫的理想形态:**PushKit 唤醒 + CallKit 来电式语音汇报**——电脑干完活,手机像来电话一样响,接起来就是 AI 汇报。技术选型见 [03 · 架构](03-architecture.md) §8。

## 8. 未来模式:多人 / 会议旁听(P2 预研 / P3 产品化)

把 AI 拉进一场多人电话会(如你和客户开会),两种姿态:**参与式**(需要时插话澄清)或**纯旁听**(全程只听只想,会后单独和你开小会,给出决策包,确认即开工——"明天早上起床,它交活了")。分期口径(与 05 §4 一致):P2 只做 discovery(合规/说话人分离/授权模型预研 + 被动旁听实验),P3 才产品化。

未来产品化前必须先立的边界契约(不写清就会把多人会议误建成"一段更长的用户输入"):

- **同意**:全体知情同意,且按用途/保留期逐项同意;第三方语音默认只作本地理解、不外泄,撤回要传播;
- **说话人与立场**:说话人分离 + 谁说的记谁(speaker/role/stance),第三方话语**永远不能**变成用户偏好或授权(呼应 04 §1.4);
- **授权**:会上"大家听起来都同意"不等于授权——决策 owner 的 Authority key 仍单独走(04 §2.5);
- **共享/私密分层**:会议共识与 owner 私下顾虑分层存放,对外输出按受众过滤。
