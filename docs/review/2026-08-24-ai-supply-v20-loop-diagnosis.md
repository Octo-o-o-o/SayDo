## 2. 不可收敛的三项结构证据

### 2.1 这不是设计文档,是藏在 Markdown 里的 4.5 万行 TypeScript

| 指标 | 实测 | 占全文 |
|---|---|---|
| 全文 | 48,809 行 | 100% |
| 代码块(fence)内行数 | 45,822 行 | **93.9%** |
| §4「目标架构」(182–43,635 行) | 43,453 行 | **89.0%** |
| 最大单个代码块(205–24,488 行) | **24,283 行** | 49.8% |
| 次大代码块(27,514–40,144 行) | 12,630 行 | 25.9% |

横向对比(同为本会话实测):

- 真实 `packages/contracts` 整包:**5,040 行** → 那一个 24,283 行的代码块是它的 **4.8 倍**
- 全仓 `packages/**/*.ts`:**119,543 行** → 本文档代码块占全仓生产代码的 **38%**

一个 24,283 行的单一代码块,不存在「零上下文审查者能正确审完」的可能,也不存在
「改一处不牵动别处」的可能。

### 2.2 A 级计数是随机游走,不是收敛曲线

按版本提取各路终审的 A 计数(缺格为该轮报告未用统一格式书写头部):

```
v9 :3      v10:7      v11:4      v12:2      v13:1      v14:9
v15:3      v16:2/4/4  v17:4/2    v18:5/2    v19:8/1    v20:4/1/6
```

v13 一度降至 A=1,v14 立刻反弹至 A=9。20 轮「final closure」零次 PASS。
这与「逐轮逼近」的形态不符,与「对固定巨兽做独立随机采样」的形态吻合。

### 2.3 早期能 PASS 的版本,是被自身膨胀撑垮的

`history/PROCESS-JOURNAL.md` R98 记述:早期方案 182,627 bytes,
SHA `10926595…f318dd`,结论为「评审通过,无未处置 A 级」。
(注:该版本文件已被覆盖,本会话无法直接复现其编译结果,此处仅引用 journal 记述。)

当前 3,022,748 bytes = **膨胀 16.5 倍**。R99 已自行判定 R98 的 PASS 不再代表现状。
即:规模增长本身是失控主因,而 v21 的既定动作(补全 8 条根因)只会继续增大文档。

## 6. 建议路线

### 6.1 立即(需 owner 授权 commit)

将现有 20 轮产物按原样纳入版本控制,作为过程档案冻结。不修订、不删减,只保全。

### 6.2 改道:拆分审查对象

把当前单一 3 MB 文档拆成两类各自可验证的产物:

- **决策文档**(人读,目标 ≤ 800 行):§0 开工纪律、§1 结论、§2 审计、§3 旅程、§9 生态清单、
  §10 分阶段计划、§14 决策点、§16 定义完成。这部分才适合「人 + 对抗审查」。
- **合同代码**(机器验,进 `packages/contracts` 真实源码树):§4 的 4.3 万行下沉为真实
  TypeScript 文件,由 `tsc` + `vitest` + fixture 验证。真实代码的正确性由测试证明,
  不由「零上下文审查者读 2.4 万行代码块」证明。

拆分后,现有 v20 三路 finding 里绝大多数会自动转为「真实代码里的待修 issue」,
可逐个用测试锁定,而不是每轮重新被随机发现。

### 6.3 真正的关键路径:先签 §14 十项决策

十项决策不依赖 v21,也不依赖合同代码收敛;反过来,**它们决定合同该怎么写**。

这些决策不是「文档尾部的附注」,而是贯穿 §4 数千行合同的活跃变量。
