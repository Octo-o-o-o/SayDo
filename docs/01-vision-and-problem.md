# 01 · 背景与问题(Vision & Problem)

> 本篇回答三件事:这个项目为什么存在、它解决什么问题、凭什么"现在"能做成。
> 下一篇:[02 · 产品定义](02-product-definition.md)。全部引用与出处见 [06 · 参考资料](06-references.md)。

## 1. 一句话定位

**SayDo 是一个你能对着说话的高级助手**:你只管把事聊清楚(甚至聊的过程中才想清楚),它先吃透项目上下文,听懂了就主动提议开始,驱动本地 AI agent 把事办成,跑完等你验收时叫你。

它**不是**:语音问答机器人、"语音转文字"的输入法、NotebookLM 式资料问答、或一个"更好的指令翻译器"。核心竞争力不在用哪个模型,而在 **context 工程 + 人机协作流程设计**。

## 2. 背景:两个同时到位的技术拐点

同一个想法放在 2025 年不成立,放在 2026 年成立。本项目依赖两个"刚刚成熟"的能力,缺任一者,产品都会退化成"语音版 ChatGPT"或"不靠谱的自动脚本":

1. **够自然的实时对话模型**:OpenAI Realtime(gpt-realtime)/ GPT-Live、Gemini Live 等 speech-to-speech 模型,以及 Fable 级文本旗舰 + 流式 ASR/TTS 的级联管线——能打断、能长时对话、能边听边想,让"人把虚的事聊透"这一步顺畅到值得依赖。
2. **够强的自主执行 agent**:Claude Code(Agent SDK / headless CLI)、Codex(`codex exec` / app-server)、Cursor(`@cursor/sdk`)都提供了程序化接口——结构化事件流、会话恢复、中断(运行中追加指令的能力三家不同,见 03 §5),让"AI 自己把实的事做完"真的能交活。

6 路竞品调研(2026-07)证实:这条链路的**每一块都已有更成熟的单点实现;在截至 2026-07-22 的已审样本中,尚未发现把"聊透→自动开工→隔夜交活"按同一套治理闭环做全的产品**——这既是可行性证据,也是机会窗,但不是全市场的存在性证明(最接近的近邻如 Paseo 已覆盖本地 daemon/多 runner/语音/手机遥控的大部分链路;详见 [05 · 落地与路线](05-roadmap.md) 与 `../research/`)。

## 3. 要解决的问题

| # | 痛点 | 现状 |
|---|---|---|
| P1 | **指令是有损压缩**:人在"指派任务"时思路越来越窄,把丰富、模糊的想法压成一句话;多数人(包括老板)本来就给不出好指令 | 现有 AI 工具几乎都要求用户"把需求说清楚"(prompt 工程、spec 表单、结构化输入) |
| P2 | **空脑袋对话**:系统没有项目持久记忆,每次对话等于 ChatGPT 新开窗口,对项目一无所知 | 上下文靠用户每次手动粘贴/重述;聊过的知识不沉淀 |
| P3 | **对话不收敛**:越聊越发散,聊完没有行动;没有人(或机制)判断"信息已经够了,可以开工了" | 何时开工、怎么开工全压在用户身上 |
| P4 | **执行是同步的**:人必须守在屏幕前看 agent 干活,走开了就断;agent 完成/卡住时没人知道 | 无回叫机制;异步协作断裂 |
| P5 | **打字是瓶颈**:表达带宽低、场景受限——路上、沙发上、会议间隙无法推进工作 | 语音输入普遍只是"转文字",不是双向对话 |

这五个痛点共同指向一件事:**人与 AI 的协作范式还停留在"人下指令、人盯执行"**,而模型能力已经支持"人只管聊、AI 自懂自做、做完叫人"。

## 4. 设计哲学:对话优先于指令(第一性原理)

三条原理统领全部设计(用户原始洞察全文见 `../history/scenarios/design-philosophy-conversation-over-instruction.md`):

1. **指令是有损压缩,对话是逐步展开。** 指派 = 把脑子里丰富的想法压成一句话(收窄、丢信息);对话 = 在来回中把想法展开补全(完善、增信息)。做"大而模糊"的事,对话天然优于指令。
2. **不要求用户会下指令。** 与其教用户写好 prompt、帮他把指令翻译得更好,不如取消"下指令"这个前置:你只管聊,AI 聊到自己懂了、准备够了,**主动提议开始并自己把事办成**。
3. **AI 是高级助手,不是指令翻译器。** 心智模型是"天天和你聊天、听懂就自己把事办成的**幕僚长**(chief of staff)",不是"你说得越清楚我做得越好的执行器"。

由此派生三个贯穿全文的设计立场:

- **规格是 AI 的产物,不是用户的输入。** 任务卡/spec 仍然存在,但它是 AI 聊天后自己沉淀的,用户永远不必"写规格"。
- **认知负担转移:从"表达"到"判断"。** 不让用户凭空把需求说全(难),而是让用户看着具体的东西——【成果预览 + 实施计划 + Demo】——说"对 / 不对 / 调一下"(易)。确认是审阅式的,不是规约式的。
- **发散与收敛有节奏。** 聊天阶段允许发散(思路完善);AI 在背后每轮判断火候,**知识与需求两个维度都够了才收敛**,不过早逼用户拍板。

## 5. 目标体验(两个用户故事)

**故事一:工程师的一天。** 早上 9 点,你端着咖啡对电脑说:"把昨天说的导出功能做了,用 CSV,验收标准是 Excel 能直接打开。"它带着对代码库的理解追问两句(放哪个菜单?要不要表头?),复述一遍,你说"去干吧"。40 分钟后电脑开口:"执行和检查都跑完了,等你验收——改了 5 个文件,12 个测试全过,有一个设计决策要确认。"你说"讲"——它讲完,你说"开 diff 我看看……第三个文件函数名改一下,然后提交"。它照做,回叫:"提交好了,要发 PR 吗?"(合并永远由你拍板,它不自称"做完"。)

**故事二:老板的隔夜交活。** 你有一件大而模糊的事,不知道怎么"布置"。你只是和它聊——把背景、顾虑、期望零零碎碎说出去,它一边听一边自己研究、自己攒资料。聊到某一轮,它说:"我觉得可以开始了。做完你会得到这些(口头 + 一个可视化 Demo),我打算分这几步做,其中两步需要你配合(给凭据、拍板对外口径)。现在开始吗?"你看了 Demo 说"就这样"。睡觉。第二天早上,它交活了。

> **承诺口径(诚实分档,owner 2026-07-24 裁定)**:故事二是**愿景叙事**;首发对外只承诺**前两档**——① 后台尝试(可离开,卡住/越界会叫)② 给出可审阅成果(到 `ready_for_review`,带逐条验收证据)。**③ 经你验收交付**(合并/归档)始终在你手里、不自动。"睡觉、第二天交活"描述的是①②的体感(离开→回到验收点),**不承诺可靠完成任意隔夜 workflow**(可靠多步/跨长时恢复/移动验收未全落地,见 04 §6);营销文案可说"离开到验收点",不得暗示无人值守完成。

## 6. 可行性结论

**可实现。** 三个核心能力在 2026 年全部成熟(逐点核实见 [03 · 架构](03-architecture.md) 与 [06 · 参考资料](06-references.md)):

1. 双向实时语音对话(流式、可打断、亚秒首响)——级联与 speech-to-speech 两条路线都成熟;
2. 无头驱动本地编码 agent——三家(Claude Code / Codex / Cursor)都有结构化事件流、恢复、中断;
3. 完成后"叫人"——语音回叫 / 桌面通知 / 手机推送 / 电话,通道齐备。

真正的工程难点不在"能不能",在以下六处(机制详见 [04 · 关键机制](04-key-mechanisms.md)):

| 难点 | 一句话 |
|---|---|
| 分层记忆与项目奠基 | 项目要有持久、可生长的知识库——这是与"ChatGPT 新窗口"的分水岭 |
| 语音会话经济学 | 长任务期间不能保持语音连线;会话短命、任务长命,两者解耦 |
| 就绪判定的可信性 | 防"相关错误链":判断"够不够开始"的机制必须与生成/执行解耦、可校准 |
| 审批与失控防护 | 语音是弱认证通道;无人值守期间要防烧钱、防危险命令 |
| 口播摘要 | 几百条 agent 事件如何变成 30 秒能听懂的话 |
| 跨设备与恢复 | 手机沟通端 × 桌面执行端的安全连接、断线恢复、跨边界事务 |

## 7. 范围与非目标

**范围**:服务"**有明确产出物的项目**"——代码 / 文档 / 报告 / 文章 / 方案 / 计划,每种类型都有清晰的产出与验收标准。编码开发是主场景,但同一套上游能力(奠基、采访、就绪决断、回叫、沉淀)服务多种项目类型(见 [02 · 产品定义](02-product-definition.md) §5)。

**非目标**:

- 不做通用语音助手(闹钟、闲聊、放歌),不追求漫无目的的陪伴;
- 不替代 IDE:细节(diff、日志、长文档)永远转屏幕看,语音只承载**决策和摘要**;不做"语音念代码";
- P0 单用户;多人/会议旁听是未来模式(P2 预研 / P3 产品化,见 02 §8);
- P0 不做手机原生 App(用推送 + 浏览器页面顶替;移动端原生外壳排 P1,见 03 §8)。
