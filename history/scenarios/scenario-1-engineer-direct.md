# 场景 1:工程师直接沟通,开始开发(传统主线)

> 状态:主方案 v1.4 **已基本覆盖**(这是 §1.1 用户故事的主线)。本文件用于回归校验。

## 一句话

一个懂技术的工程师,像和同事口头交代活儿一样把需求说清楚,系统澄清确认后派本地编码 agent 开发,做完叫他验收合并。

## 角色与前提

- **主角**:工程师,懂技术、能看懂 diff、能用技术语言下指令(甚至直接点名"用 Codex 跑""改 `ReportTable`")。
- **前提**:目标 repo 已存在、可编译可测试;工程师对代码库有基本了解。

## 期望完整流程

1. 选中/提及一个 repo,开麦(或按住说话)。
2. daemon 后台做 Context 预研,Brain "读过项目"。
3. 工程师口述需求——通常已经比较具体("给报表页加 CSV 导出,带表头,UTF-8 BOM,别引新依赖")。
4. 采访很轻:Brain 只补关键缺口(放哪、验收标准),不啰嗦。
5. Brain 复述任务卡的 goal + 验收标准,工程师说"对,派 Claude"。
6. daemon 建 worktree → 派 coding agent → 后台执行,事件流入库,摘要器工作。
7. 完成/阻塞时回叫;工程师听 30 秒摘要 + 决策清单,必要时 `open_on_screen` 看 diff。
8. 工程师口头给修改意见(steer / kill_and_resume)或验收;说"合并"→ MERGING(rebase+重跑 verify)→ done,或开 PR。

## 全程产物(应持久化)

任务卡 / spec、事件流 JSONL、diff.patch、测试结果、decisions[]、会话转写、commit/PR 链接。

## 验收标准

全程除 L3 审批和点击开麦外不碰键盘,完成一个真实小需求的"口述→确认→等待→听汇报→验收合并"闭环。

## 与主方案的差异 / gap

几乎无。唯一小缺口:一次口述包含多个任务时的自动拆分与并行调度入口。属增强,不阻塞。
