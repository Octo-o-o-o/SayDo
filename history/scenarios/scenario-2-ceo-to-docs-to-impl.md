# 场景 2:非技术负责人捋思路 → 生成完整开工文档体系 → 开始实施

> 状态:主方案 v1.4 **覆盖不足**,是本轮完善的主要驱动之一。

## 一句话

一个非工程师(CEO / 产品负责人)带着想清楚的业务思路来,和系统对话,先**产出一整套开工文档**(PRD、技术架构、任务分解、里程碑、开工检查单),审阅修订满意后说"开始实施",系统把文档体系转成一批编码任务派下去。

## 角色与前提

- **主角**:CEO / 产品负责人。有清晰的业务/产品思路,但**不写代码、不看 diff**,用业务语言表达,验收的是"文档对不对、思路全不全",不是"测试过不过"。
- **前提**:可能是全新项目(空仓库或还没有仓库),也可能在既有产品上加大功能。

## 期望完整流程

1. 开麦:"我想做一个面向 X 用户的 Y 产品,核心是 Z……"——先讲业务思路。
2. **深度采访(比场景 1 深得多)**:AI 主导,挖清楚目标用户、核心价值、范围边界、约束(预算/时间/合规)、成功标准。因为要产出完整文档,澄清必须充分。
3. **边聊边研究**:系统调研背景/竞品/(若有)现有代码库,把 context 补厚;调研中间产物随时落库。
4. **产出开工文档体系**(一等产物,不是口头总结):
   - PRD(产品需求文档):目标、用户、功能列表、优先级、验收标准;
   - 技术架构文档:技术选型、模块划分、数据模型、接口、风险;
   - 任务分解 + 里程碑:WBS、依赖、排期;
   - 开工检查单:环境、仓库、CI、分工。
   这些文档**落盘、可在屏幕查看、可版本化迭代**。
5. **协同审阅**:CEO 在屏幕看文档 + 语音提意见("架构里把支付单独拆个服务""里程碑压到 6 周"),多轮修订,每版留痕。
6. CEO 说"可以,按这个干"→ 系统把文档体系**自动拆解成一批编码任务卡**(承接场景 1 的执行闭环),多任务并行/排队。
7. 实施期回叫 CEO 做**业务级决策**(不是技术细节):"登录要不要支持微信?这会影响两个里程碑。"
8. 阶段性产出(可跑的功能、demo)回报;CEO 验收的是"是不是我要的东西",可再提需求回到修订。

## 全程产物(应持久化)

PRD、架构文档、任务分解、里程碑、开工检查单(各含多版本)、调研/竞品资料、决策记录、会话转写 + 后续所有代码产物。全部归入同一个**项目**,可随时调阅。

## 能力要求 checklist(拿来对账主方案)

- [ ] **"项目"层级**:一个项目 = 一批文档 + 一批任务 + 一批产物(当前只有扁平的"任务卡")
- [ ] **规划/文档产出作为一等阶段**:对话 → 生成文档体系 → 评审 → 再实施(当前直接对话→单任务→改代码)
- [ ] **结构化文档产物 + 版本化 + 屏幕协同审阅**(当前 §4.15 偏"结束时导出一份 Markdown")
- [ ] **文档 → 任务分解 → 批量派单**的桥
- [ ] **非技术用户适配**:验收基于文档/业务而非 diff/测试;审批用业务语言;不强迫看代码
- [x] 深度采访能力已有雏形(§4.3),但要支持"以产出完整文档为目标"的长采访
- [x] Context 预研 / 调研能力可复用(§4.1)
- [ ] **产物随时召回**:CEO 说"上次那版架构再给我看看"能立刻调出(依赖横切产物库)

## 验收标准

非技术用户全程用业务语言,产出一套内部自洽、可直接开工的文档体系;说"开始"后能无缝进入实施且能被叫回做业务决策。

## 与主方案的差异 / gap(驱动 v1.5)

1. 缺"项目"层级抽象;
2. 缺"规划产出"阶段与文档类产物模型;
3. 缺"文档→任务批量转化"的桥;
4. 缺非技术用户的验收/审批表述;
5. 文档协同审阅与版本化未设计。
