# VoiceLoop 场景库(交叉 review 用)

这些文件把用户口述的目标场景固化下来,作为**需求基线**和**交叉 review 的 checklist**——每次主方案(`../voice-coding-framework.Cursor2.md`)迭代后,回来逐条对照每个场景的"能力要求 checklist",看方案是否还覆盖得住。

|---|---|---|---|---|
| 1 | `scenario-1-engineer-direct.md` | 工程师直接口述需求,派 agent 开发 | 工程师(懂技术) | 代码改动 / PR |
| 2 | `scenario-2-ceo-to-docs-to-impl.md` | 非技术负责人捋思路,先生成完整开工文档体系,再实施 | CEO / 产品负责人 | 项目文档体系 + 后续代码 |

## 三个场景的关系(为什么它们一起出现)

它们是**同一个工具的能力光谱**,由窄到宽压测同一个假设——"VoiceLoop 到底是不是只能做编码?":

- 场景 1 = 当前主方案的主线(编码,技术用户,直接执行);
- 场景 2 = 把"规划/文档产出"提到执行之前,且主角是非技术用户(编码仍是下游);
- 场景 3 = 连"下游是编码"这个假设都去掉(产出是任意任务计划与内容产物)。

横切的产物持久化是让 2、3 成立的地基:文档、调研资料、方案本身都是"产物",必须全程可存、可查、可召回。

## 使用方式

1. 读主方案后,拿每个场景文件末尾的 **"能力要求 checklist"** 逐条打勾;
2. 打不了勾的就是 gap,记入主方案的迭代记录;
3. 场景文件是"应然"(需求),主方案是"实然"(设计),两者独立存放便于对账。
