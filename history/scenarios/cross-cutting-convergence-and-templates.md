# 横切:对话收敛(反发散)与项目类型模板

> 状态:用户 2026-07-22 提出的两个关联想法,主方案 v1.8 据此新增 §4.20、强化 §4.16。本文件记录洞察 + 深挖(供交叉 review)。

## 1. 用户原话洞察(忠实记录)

**想法 A —— 收敛式对话 + 就绪决断 + Demo 预览(反发散):**
- 人和 AI 聊天不应一直发散、扩散。
- 大模型**每次回答结束时都反思**:现在积累的上下文,是否已经可以**完美实施**用户的需求了。
- 若可以:给用户一个**可审阅的方案**,告诉用户"已经准备好了"——如果都完成,用户会**得到一个什么样的东西**、会**按哪些步骤做**,并且**如果可能用一个 Demo HTML** 展示用户最终会得到什么。
- 目的:**避免过度发散、让事情偏离原始轨迹**。用户可能不知不觉已提供了足够信息,AI 帮做这个决断——"要不要现在就开始?"
- 提供的【实施计划 + Demo HTML + 完美实施后会得到什么】是用户**有效做决策的重要依据**。

**想法 B —— 预制多套项目类型模板(是"类",不是固定 workflow):**
- 最开始预制多套模板:开发项目、营销项目、调研项目……这一类。
- 模板**不是完全固定的 Workflow**,不是"一步步怎么做";它主要让大模型**最开始就知道现在要做的是什么类型的事情**。
- 明确了类型之后,才能把"帮用户决断要不要开始"做清楚——因为**开发/调研/营销项目,"能否开始、上下文是否足够",判定标准都不一样**。

## 2. 两个想法的关系

**B 是 A 的前提。** "就绪没有"不是一个通用判断,而是**类型相关**的:开发项目要目标+验收+代码库理解到位,调研项目要问题+范围+信息源到位,营销项目要受众+渠道+调性到位。所以必须先识别类型(B),才能拿该类型的"就绪清单"去做每轮自省与就绪决断(A)。

## 3. 深挖:项目类型模板(强化 §4.16)

模板是**软的思考框架**,不是硬 workflow。每个模板定义四样:

| 模板要素 | 说明 |
|---|---|
| 识别线索 | 怎么从用户开场判断属于这一类(关键词、意图) |
| **就绪清单(readiness checklist)** | 该类型"可以开始"前必须澄清/准备到什么程度——**这是 A 的判定依据,每类不同** |
| 产出物形态 | 最终交付长什么样(已在 §4.16) |
| **Demo 形态** | 用什么向用户预览"最终会得到什么" |

就绪清单示例(节选):

- **开发**:目标、验收标准(可验证)、涉及范围、约束、代码库关键部分已理解 → Demo:可点的 HTML 原型
- **调研**:调研问题、范围与深度、交付形式、信息源可及 → Demo:报告大纲 + 一节样章
- **营销**:目标与成功指标、目标受众、渠道、预算、调性 → Demo:方案一页纸 + 样例素材/落地页 mock

模板只提供"框架 + 就绪标准",具体怎么走仍由大模型按对话灵活决定(不固化步骤)。

## 4. 深挖:收敛与就绪决断循环(新增 §4.20)

**问题**:开放式采访(§4.3)若无终止条件,会一直发散,偏离用户原始意图。

**机制(每轮回答末尾)**:

1. **就绪自省**:Brain 对照当前类型模板的就绪清单,评估"够不够完美实施"。
2. **未就绪** → **定向收敛**:继续问,但只朝补齐就绪清单缺口的方向问(收敛式,不发散)。
3. **就绪** → **产出决策包(Decision Package)**,主动请求 go/no-go:
   - **成果预览**:完美实施后你会得到什么(一句话 + 要点);
   - **实施计划**:会按哪些步骤做(对开发=任务分解,对调研=调研计划,对营销=执行步骤);
   - **Demo(可能的话)**:一个 HTML demo 展示最终样子(UI/产品类最有效;非 UI 类用报告样张/方案一页纸/流程图替代);
   - 明确问:**"要不要现在就开始?"**
4. 用户据决策包做 go / 再改 / 补充。

**定位**:这是"防发散、防偏离原始轨迹"的核心收敛器,也是采访模式(§4.3)的**终止条件**。决策包三件套(计划 + Demo + 成果预览)是用户有效决策的依据——比纯文字"我准备好了"强得多,因为用户能**看到**将得到什么。

**边界**:Demo 是轻量、可抛弃的预览(mock 数据/假交互),不是真实施;生成便宜。不强求所有项目都有可交互 Demo。

## 5. 与现有机制的衔接

- 依赖 §4.16 项目类型(先识别类型,才有就绪标准);
- 是 §4.3 采访的终止条件(把"聊够了"变成明确的 go/no-go 决策点);
- 决策包的"实施计划"= 确认后即可 dispatch 的东西(开发→任务卡/分解;planning→文档体系;research→调研计划);
- "成果预览 + Demo" 让 §4.16 的验收标准具象化(用户看过 demo 就知道验收成什么样);
- 新增工具 `propose_start`(§4.2)承载"产出决策包并请求开始"。
