## 0. 结论(TL;DR)

> **设计哲学:对话优先于指令(v1.10 立为第一性原理,统领全文)。** 三条:
> 1. **指令是有损压缩,对话是逐步展开**——人在**指派任务**时思路越来越窄(把丰富想法压成一句话),在**沟通**时思路越来越完善(来回中把想法展开补全)。所以做"大而模糊"的事,对话天然优于指令。
> 2. **不要求用户会下指令**——多数人给不出好指令(连老板都说不清)。与其帮他把指令翻译得更好,不如取消"下指令"这个前置:你只管聊,AI 聊到自己懂了、准备够了,**主动提议开始并自己把事办成**。
> 3. **AI 是高级助手,不是指令翻译器**——心智模型是"天天和你聊天、听懂就自己把事办成的幕僚长",不是"你说得越清楚我做得越好的执行器"。
>
> 这是一次方向修正:此前版本(及生态里 OpenClaw 的 Spec Triad、OctoDesk 的 draftWorkPlan)本质都在"把用户输入翻译成更好的规格"。新方向**不推翻规格,而是转移重心**——任务卡/spec 从"用户要费力提供的输入"变成"**AI 聊天后自己沉淀的产物**",用户永远不必写规格。详见 §14 与 `scenarios/design-philosophy-conversation-over-instruction.md`。

**这个工具是可实现的。** 三个核心能力在 2026 年都已成熟:

1. **双向实时语音对话**(不是"语音转文字输入框"):有两条成熟路线,做成**可插拔的语音引擎**(§2.1)——**(默认)级联管线**:流式 ASR + 文本 LLM(带工具)+ 流式 TTS,成本低一个数量级、工具调用走文本确定性强、可本地化;**(增强)Speech-to-Speech**:OpenAI Realtime(`gpt-realtime` 系列)原生语音进语音出,延迟更低更自然,但贵、对话行为偏黑盒。两者都能达成"流式 + 可打断 + 亚秒首响"的对话感。
2. **无头驱动本地编码 Agent**:Claude Code(Agent SDK / `claude -p --output-format stream-json`)、Codex(`codex exec --json`)、Cursor(`@cursor/sdk` / `cursor-agent`)三家都提供了程序化调用接口:结构化事件流、会话恢复、中断。**但"运行中交互式审批"三家能力截然不同**,适配层按两级集成设计(§4.4),不能假装通用。
3. **完成后"叫人"**:控制台在线时直接重建语音会话、由大脑亲口播报并等人接话;人不在时走桌面通知 + 手机推送(ntfy),人应答后注入上下文继续对话。

真正的工程难点不在"能不能",而在这几处:**分层记忆与项目奠基**(项目要有持久、可生长的知识库,而非每次从零开聊——这是与"ChatGPT 新窗口"的分水岭,见 §4.19)、**语音会话的经济学**(长任务期间不能保持连线)、**审批与失控防护**(语音指令能不能授权危险操作、无人值守期间怎么防烧钱/危险命令)、**口播摘要**(几百条 agent 事件如何变成 30 秒能听懂的话),以及合并同源方案后补强的工程底盘——**回声消除与打断体验**、**检测 agent 卡住并救回**、**合并冲突常态化处理**。本文档围绕这些展开。

> **一句话定位**(v1.2/v1.3 演进,v1.5 扩展,v1.10 收束):VoiceLoop 不是"语音问答机器人",也不是 NotebookLM 式的资料问答,更不是"更好的指令翻译器";它是**一个你能对着说话的高级助手**——你只管把事聊清楚(甚至聊的过程中才想清楚),它先吃透上下文、听懂了就主动提议开始、自己把事办成、做完叫你。核心竞争力不在用哪个模型,而在 context 工程与人机协作的流程设计。交互范式是"AI 采访人 / 幕僚长"(§9.4 实证)。
>
> **v1.5 范围扩展(关键)**:此前版本把自己锁定为"编码开发工具"。经三个目标场景(`scenarios/`)压测,范围放宽为**支持多种项目类型**——编码开发是主场景,但同一套上游能力(采访、Context 预研、回叫、摘要、产物持久化)也服务于**规划/文档产出**(场景 2:非技术负责人先出一整套开工文档再实施)和**非开发项目**(场景 3:调研、营销等,产出是任务计划与内容而非代码)。因此 worktree / verify 测试 / PR 等被降级为"**编码类型**的具体实现",不再是全局假设;产物模型与验收标准按项目类型切换(§4.16)。
>
> **v1.8 收敛原则**:对话是**收敛式**的,不发散。每轮回答后 Brain 反省"是否已够开始",够了就主动给一个【成果预览 + 实施计划 + Demo】的决策包请用户拍板"开始吗"(§4.20)——防止越聊越远、偏离原始意图。而"够不够开始"因项目类型而异,故先有项目类型模板(§4.16)识别"这是哪一类事",再有类型专属的就绪判定。

## 1. 需求拆解与范围

### 1.1 用户故事(目标体验)

> 早上 9 点,你端着咖啡对电脑说:"把昨天说的导出功能做了,用 CSV 格式,验收标准是导出的文件能被 Excel 直接打开。" 工具追问两句(放哪个菜单?要不要带表头?),复述一遍任务,你说"对,去干吧"。它回答"好,我派 Claude Code 去做,做完叫你,你忙别的"。
>
> 40 分钟后,电脑播报:"导出功能做完了,改了 5 个文件,12 个测试全过,有一个设计决策要跟你确认。" 你说"讲"。它说:"日期格式我用了 ISO 8601,因为现有代码里两种格式混用,我选了多数派,要改吗?" 你说"不用,把 diff 开给我看看"。编辑器里弹出 diff。你扫了一眼说"第 3 个文件里那个函数名改成 exportAsCsv,然后提交"。它照做,回叫:"提交好了,分支 feat/csv-export,要发 PR 吗?"

### 1.2 需求 → 能力映射

| 用户原始需求 | 精确化后的技术需求 |
|---|---|
| "对话,而不是语音转文字再回复" | 流式语音会话:边说边理解、可随时打断对方、亚秒级响应、自然轮替。**不要求**学术意义上的全双工(双方同时说话且互相理解) |
| "调本地的各种 Agent 去开发" | 无头(headless)驱动 Claude Code / Codex / Cursor:派发任务、监听进度、中断、追加指令、恢复会话 |
| "开发完再叫人" | 事件驱动的回叫:任务完成/阻塞/失败时主动通知(播报、桌面通知、手机推送),人应答后恢复对话 |
| "人再和它对话,然后继续" | 会话状态持久化:任务卡、对话转写、agent 会话 ID 都落盘;新语音会话能注入历史上下文,无缝续聊 |

### 1.3 非目标(Non-goals)

- 不做通用语音助手(闹钟、闲聊、放歌)。
- P0 单用户;**多人 / 会议旁听模式**(把 AI 拉进一场多人电话会,旁听或可打断,会后单独开小会给决策包)从"绝不做"松绑为**未来交互模式**(§4.21,v1.12 起)。
- 不替代 IDE:细节(diff、日志、长文档)永远转屏幕看,语音只承载**决策和摘要**。
- P0 不做手机原生 App(用 ntfy 推送 + 浏览器页面顶替)。
- 不做"语音念代码"/"语音念长文档"。
- (v1.5)**不做无边界通用助手**:虽然支持多种项目类型,但只服务"**有明确产出物的项目**"(代码 / 文档 / 报告 / 方案 / 计划),每种类型都必须有清晰的产出与验收标准;不追求漫无目的的闲聊陪伴。

## 2. 可行性论证(逐点核实)

### 2.1 双向语音对话层:可插拔双引擎

"对话感"的判定标准是三条,与内部实现无关:**流式低延迟**(说完到出声 P50 ≤1.5s / P90 ≤2.5s)、**可打断(barge-in)**、**多轮澄清**。两种引擎都能达成,对上层暴露同一接口(`say()` / `on_user_utterance()` / `interrupt()`),大脑层不感知差异。

**引擎 A:级联管线(v1.4 起改为默认)**

```
麦克风 → VAD → 流式 ASR ──文本──→ 大脑(文本 LLM + 工具) ──文本──→ 流式 TTS → 扬声器
```

- 全链路流式:ASR 边说边出、LLM 流式出 token、TTS 按句合成首句先播。开源可用 Pipecat / LiveKit Agents 编排,Silero VAD(~30ms),STT/TTS 走可替换 Provider(云:火山/Paraformer/gpt-4o-transcribe;本地:MLX Whisper / FunASR;TTS 本地兜底 piper/kokoro/`say`)。
- **为什么改为默认**(v1.4 合并后的重估,理由见 §10):① 成本低一个数量级(§7);② **工具调用走文本 LLM,确定性远高于语音模型**——这正好化解本方案 §8 R4 的担忧(不信任语音模型的结构化输出),级联下 `create_task/dispatch` 等由文本旗舰模型执行;③ 每一环可独立替换/本地化;④ 同行产品实证(§9.4)界面带 "Live transcript"(实时转写)+ "Done speaking",backend=codex、model=gpt-5.6-sol-max,形态更接近级联而非纯 S2S。

**引擎 B:Speech-to-Speech(增强选项)**

- OpenAI Realtime(`gpt-realtime` 系列):原生语音进语音出、WebRTC 直连、服务端 VAD 轮替与 barge-in、function calling(`session.update` 注册 / `response.done` 取参 / `conversation.item.create` 回注)。**单会话上限 60 分钟**,浏览器端须用 **ephemeral key**。
- 定位:对话体验天花板,延迟可到 1s 内,但成本高一个数量级、行为偏黑盒。作为可选配置项,追求极致自然度时启用。

**回声消除(AEC)与打断——外放模式的硬工程点(v1.4 合并补强)**。外放扬声器时若无 AEC,TTS 声音会被麦克风收回导致"自我打断",必须解决。按省力程度排序的降级链:

1. **耳机 / 按住说话(PTT)**:无需 AEC,P0 最简起步;
2. **本地 Web 音频前端(推荐)**:控制台页用 `getUserMedia({echoCancellation:true})` 借浏览器工业级 AEC,音频经 WebSocket 进 daemon,顺带得到状态可视化 UI——这也正是本方案控制台走浏览器的额外理由;
3. **原生 VoiceProcessingIO**:需独立 Swift helper,外置 USB 麦兼容性差,失败自动降级;
4. **webrtc-audio-processing 软件 AEC**:需手工对齐远端参考信号与采集延迟,深坑,最后选项。

> 真全双工模型(Moshi 类)不需要——VAD 轮替 + barge-in 已满足对话感。

### 2.2 Agent 驱动层:能力矩阵(已核实)

| 能力 | Claude Code | Codex CLI | Cursor |
|---|---|---|---|
| 无头一次性执行 | `claude -p "..."` | `codex exec "..."` | `Agent.prompt()` / `cursor-agent -p` |
| 结构化事件流 | `--output-format stream-json`(含部分消息) | `--json`(`thread.started` / `turn.*` / `item.*` / `error`) | SDK `run.stream()` 消息流 |
| 常驻多轮进程 | [ok] Agent SDK streaming input mode | [fail] (一轮一进程) | [ok] `Agent.create()` + 多次 `send()` |
| 运行中注入指令(steering) | [ok] (流式输入注入新消息) | [fail] | [fail] (先 `run.cancel()` 再 `send()`) |
| 中断 | [ok] SDK `interrupt()` | [warn] kill 进程 | [ok] `run.cancel()` |
| 跨进程恢复会话 | [ok] `--resume <session_id>`,可 fork | [ok] `codex exec resume <id> / --last` | [ok] `Agent.resume(agentId)` |
| 逐条权限回调 | [ok] `canUseTool` 回调 + hooks | [fail] (启动前预设 `--sandbox` / approval 策略) | [warn] `.cursor/hooks.json`(配置式) |
| OS 级沙箱 | [fail] (逻辑权限;硬隔离需外挂,见 4.7) | [ok] 内置(Seatbelt/Landlock) | 本地无;cloud 为隔离 VM |
| 结构化最终结果 | `--output-format json` | `--output-schema` + `-o file` | `run.wait()` → `RunResult` |

三家都满足最低要求(启动/事件流/恢复/中断)。差异(steering、权限回调)由适配器层抹平,见 4.4。

**结论:可行。** 且 Claude Code 的能力最全,适合做 P0 首个适配器。

### 2.3 回叫(叫人)通道

| 通道 | 实现 | 时延 | 适用 |
|---|---|---|---|
| 语音回叫 | 重建 Realtime 会话,由 Brain 开场播报(macOS `say` 仅作会话建立失败时的兜底提示) | 秒级 | 人在电脑旁/控制台在线 |
| 桌面通知 | `osascript display notification` / terminal-notifier | 秒级 | 人在电脑旁但戴耳机/静音 |
| 手机推送 | ntfy(自托管或公共服务),点击直达 Web 控制台 | 秒级 | 人离开工位 |
| 电话呼叫 | Realtime API SIP + Twilio | 十秒级 | 人彻底离线(P1) |

**结论:可行。** 关键不是通道,是策略(什么事件值得打扰人、打扰到什么程度),见 4.6。

### 2.4 总可行性裁决

全链路无"当前技术做不到"的环节。被判定**不做**的只有:真全双工自托管模型(质量不足)、语音念代码(无意义)、纯语音授权一切操作(不安全,见 4.7)。

### 2.5 为什么是"现在"(时机论,v1.12)

**同一个想法放在半年前不成立,放在现在成立**——这不是修辞,是硬前提。本方案能成立,依赖两个 2026 年才真正到位的能力:① **够自然的实时对话模型**(GPT-Realtime / GPT-Live / Gemini Live,能打断、能长时对话、能边听边想),让"人把虚的事聊透"这一步顺畅到值得依赖;② **够强的自主编码/执行 agent**(Claude Code / Codex / Cursor 的无头模式 + 长时后台执行),让"AI 自己把实的事做完"真的能交活。缺任一者,产品都退化成"语音版 ChatGPT"或"不靠谱的自动脚本"。这也是对"这想法真能做到吗"最直接的回答:**每一块都已有成熟实现(§15 竞品调研验证),只是此前没人把"聊透→自动开工→隔夜交活"这条完整链路按这个哲学串起来。**

### 3.2 组件职责

| 组件 | 职责 | 关键点 |
|---|---|---|
| **Web 语音控制台** | 承载麦克风/扬声器,浏览器 WebRTC 直连 Realtime API;渲染屏幕确认卡片、任务看板、diff 链接 | 桌面和手机用同一个页面;**麦克风要求 secure context**——桌面走 `http://localhost` 天然满足,手机必须 HTTPS(`tailscale serve` 自带证书或 mkcert),否则 getUserMedia 会被浏览器直接拒绝;Realtime 的 function call 经 data channel 收到后转发给 daemon 执行 |
| **Brain(对话大脑)** | 就是 Realtime 模型本身 + 注册在会话上的工具集 + 精心设计的 instructions | 不自己干活,做四件事:**采访式澄清/脑暴**需求、调用工具、口播摘要、把细节推屏幕。人格:简短、口语、中文、不念代码 |
| **Context 预研器**(v1.2) | 会话锚定某 repo 时,异步跑一次只读预研 pass,产出代码库概览(架构、关键模块、近期改动、疑似 TODO),缓存供 Context Pack 注入 | 让 Brain "开聊前已读过项目";预研只读、受限、可缓存复用;是"context 前置"原则的执行者 |
| **voiced daemon** | 常驻后台进程。签发 ephemeral key、执行 Brain 的工具调用、编排任务、跑适配器、发通知 | 语音会话断了它也活着,任务照跑——这是"挂断后继续开发"的基础 |
| **任务编排器** | 任务卡状态机(见 4.3)、队列、每任务分配 git worktree | 同一仓库的任务默认进同一队列串行 |
| **Agent 适配器层** | 把三家 CLI/SDK 差异抹平成统一接口:`start / events / steer / interrupt / resume / answer` | 差异降级策略见 4.4 |
| **摘要器** | 把 agent 原始事件流(JSONL)压成三层口播摘要:进度统计走纯规则,叙事层按需调廉价文本模型 | Realtime 模型永远不直接看原始事件流——太贵、上下文装不下 |
| **回叫策略引擎** | 决定"这个事件值不值得现在打扰人、用哪个通道" | 阻塞 > 失败 > 完成 > 进度;免打扰窗口 |
| **状态存储** | SQLite(任务卡/会话/审批记录)+ JSONL(事件流、对话转写) | 一切可恢复:daemon 重启后任务和会话都能接上 |

### 3.3 技术栈选型

- **daemon:TypeScript / Node 22+**。理由:Claude Agent SDK 与 `@cursor/sdk` 都是 TS 一等公民,Codex 用子进程 + JSONL 解析,统一语言最省;WS/HTTP 生态成熟。
- **语音端:浏览器页面**(daemon 静态托管)。理由:WebRTC、麦克风权限、回声消除全由浏览器解决,零原生开发;桌面手机通吃;屏幕确认通道顺便有了。菜单栏原生 App 留到 P2。
- **Brain 模型:`gpt-realtime-2.1`**;**摘要器:廉价快速文本模型**(如 gpt-5-mini 级别,可换)。
- **存储:SQLite + 文件系统 JSONL**,零运维。
- **推送:ntfy**(可自托管)。

## 4. 关键设计

### 4.1 语音会话生命周期(会话经济学)

语音会话是有成本的(级联按 ASR/TTS 分钟计费;S2S 引擎更贵,音频 token 单价是文本的数倍到数十倍,且单会话 60 分钟硬上限)。**因此设计原则对两种引擎都成立:语音会话是短命的、事件驱动的;开发任务是长命的、后台的。两者生命周期彻底解耦。** 下文中"60 分钟上限""ephemeral key"等仅 S2S 引擎适用,级联引擎无此约束但同样遵循"窗口化、空闲即挂起"以省钱省电。

```
[人点击开麦/回叫应答] ──▶ 建会话(注入上下文包) ──▶ 对话若干轮 ──▶
   派发/答疑完成 ──▶ 空闲 45s 或人说"去吧" ──▶ 挂起(关 WebRTC,零成本)
                                   任务在 daemon 后台继续跑
[任务事件触发回叫] ──▶ 控制台在线:直接重建会话,Brain 开口播报
                    控制台离线:桌面通知 + ntfy ──▶ 人点开 ──▶ 建会话 ──▶ ...
```

注意两个成本/平台细节:

- **(v1.14 事实纠正,来自 Codex 核实 OpenAI 官方文档)**:Realtime 连接/带宽本身不收费、VAD 会过滤空输入,所以"静默期麦克风持续按 token 计费"**不成立**——只有被作为 conversation input 提交的音频才计费。挂起仍取较短阈值(45 秒)但理由改为**隐私/功耗/占麦/误触发**;真正的省钱点是:每次 Response 会重带整个 conversation,后续 turn 越来越贵,所以要短会话 + 及时挂起 + Context Pack 压缩,而非担心"连接本身烧钱"。
- "挂起后对着空气说话唤醒"在 P0 **不存在**:WebRTC 断开后没人在听。P0 的唤醒动作是点击(控制台按钮/系统通知/手机推送);本地常驻唤醒词(openWakeWord)是 P2 特性。
- 回叫直接重建会话依赖浏览器约束:控制台页面必须仍开着,且用户此前已授予麦克风权限并与页面交互过(否则 autoplay/getUserMedia 会被浏览器拦截)。满足即可实现"电脑突然开口说话,人直接接话"的体验;不满足则自动降级为通知链路。会话建立后 30 秒无人应答即挂断,成本以美分计。

**上下文包(Context Pack)**:每次建会话时由 daemon 组装并注入(instructions + `conversation.item.create` 文本项):

1. 活跃任务卡列表(标题、状态、一句话进展);
2. 最近对话的滚动摘要 + 最后 N 轮转写原文;
3. 触发本次会话的事件详情(如果是回叫);
4. 仓库术语表(项目名、分支名、常用文件/模块名)——帮助 ASR 正确理解专有名词;
5. **(v1.2 新增)目标 repo 的预研摘要**:当会话锚定某个仓库时,注入由"Context 预研器"预生成的代码库概览(架构分层、关键模块、最近改动、疑似 TODO/技术债)。让 Brain 带着对代码库的理解开口,而不是零知识记录需求。

**Context 前置原则(v1.2 提出,v1.3 实证,v1.6 升级为两级)**:context 决定成败,不是模型。派单/脑暴不该在"空脑袋"状态下开始。**Context 预研器分两级**(完整记忆架构见 §4.19):

- **项目奠基(一次性,重)**:全新项目首次对话触发,深度研究并产出**持久化的项目知识底座 L1**(`.voiceloop/knowledge/`),一次建成、长期复用。这是"有价值的持续对话"与"ChatGPT 新窗口"的分水岭。
- **会话预热(每次,轻)**:已有项目开新对话时,加载已有 L1 + 按本次话题增量准备(代码库有变更则增量刷新)。

人开口时,Brain 已经"读过这个项目"。这一步把需求澄清的质量往前推了一大截——很多来回追问其实是系统不了解代码库造成的。

- **绑定 project 是 Setup 的第一要素**:实证产品(§9.4)的开聊设置里,Topic 之后紧跟的就是 Project(一个项目目录路径),开聊前必选。VoiceLoop 的控制台同样应把"选 repo"作为会话的起点。
- **预研状态要显式展示,不能静默**:实证产品在预研期间明确显示 "Researching the project for this topic before the first question... / Background research is updating the context in the background...";人知道系统在准备,而不是干等。VoiceLoop 控制台应有对应的"预研中/已就绪"状态,预研未就绪时 Brain 可以先陪聊但标注"我还在读代码"。

60 分钟上限的处理(仅 S2S 引擎):55 分钟时 Brain 主动说"我们重新连一下,马上回来",daemon 无缝重建会话并注入上下文包。实际上按本设计,单次会话很少超过 10 分钟。

### 4.2 Brain 的工具集(function calling)

**Brain 的两类行为(v1.10,按设计哲学显式建模)**:① **准备知识(proactive)**——项目奠基 + 过程中生成/调研的知识累积(§4.19/§4.18),**哪怕用户没提问也在后台攒**;② **回答问题(reactive)**——采访澄清、答疑、播报。"可以开始"的信号 = 两类**都**充分(§4.20 双维就绪)。注意:**任务卡/spec 是 Brain 在①②过程中自己沉淀的产物,不是要用户提供的输入**——用户永远不必"写规格"。

Brain(级联引擎下是文本 LLM,S2S 引擎下是 Realtime 模型)通过以下工具指挥 daemon。工具的注册方式随引擎不同(级联:普通 function-calling;S2S:`session.update` 注册),但工具集与语义一致:

| 工具 | 参数(核心) | 说明 |
|---|---|---|
| `assess_readiness` | project_id | 对照类型模板就绪清单自省"够不够开始",返回 ready / gaps[](§4.20,每轮末调用) |
| `propose_start` | project_id | 就绪时产出决策包:成果预览 + 实施计划 + Demo(可能的话),请求用户 go/no-go(§4.20) |
| `create_task` | raw_requirements(对话原话要点), repo | 创建草稿态任务卡;**规格由 daemon 侧文本模型起草**(见 4.3) |
| `confirm_and_dispatch` | task_id, agent(claude/codex/cursor/auto) | 口头确认后派发;auto 由编排器按任务类型选 |
| `get_status` | task_id? | 查任务状态(不带参数=全部活跃任务) |
| `steer_task` | task_id, instruction | 中途追加/修改指令 |
| `cancel_task` | task_id | 取消并回收 worktree |
| `answer_agent_question` | question_id, answer | 回答 agent 上浮的提问 |
| `approve_action` | approval_id, decision | 审批(仅限 L2 风险,见 4.7) |
| `explain_result` | task_id, level(one_liner/walkthrough/decisions) | 让摘要器按层级出稿,Brain 朗读 |
| `open_on_screen` | task_id, what(diff/log/pr/file) | 把细节推到屏幕(编辑器/浏览器) |
| `suspend_session` | reason | 主动挂起语音会话 |

原则:**Brain 无状态、无直接执行权**。所有副作用都发生在 daemon,工具返回值就是 Brain 的全部世界观。这保证语音层可以随时死掉重建。

工程细节:工具执行可能耗时数秒(如 `create_task` 要等文本模型起草规格)。Realtime 的函数结果是异步回注的,instructions 里要求 Brain 在调用工具后先接一句自然的过渡语("稍等,我整理一下"),避免死气沉沉的空白。

### 4.3 任务卡与口头确认协议

任务卡(Task Card)是人和 agent 之间的契约,防止"语音需求漂移":

```yaml
task:
  id: T-0042
  title: CSV 导出功能
  goal: 在报表页增加导出 CSV 按钮,含表头,UTF-8 BOM
  acceptance:
    - 导出文件可被 Excel 直接打开且中文不乱码
    - 现有测试全绿,新增导出单测
  repo: ~/work/reporting-app
  base_branch: main
  constraints: [不引入新依赖]
  agent: claude
  status: draft → confirmed → queued → running → blocked|review → done|failed|cancelled
  worktree: .voiceloop/worktrees/T-0042
```

**分工:语音模型负责对话,文本模型负责写规格。** 语音模型的指令遵循与结构化输出可靠性弱于文本旗舰模型,不能指望它口述间隙写出严谨的任务卡。因此 `create_task` 只上交对话原话要点;daemon 用强文本模型(结合本轮完整转写 + 仓库上下文)起草结构化任务卡,连同"给 Brain 的复述稿"一起返回。

**口头确认协议**:Brain 拿到复述稿后逐点复述(goal + acceptance),得到肯定答复才能调 `confirm_and_dispatch`。复述是对抗 ASR 误听和语音模型幻觉的第一道防线;派发给 agent 的 prompt 以任务卡为准,而非对话转写。

**采访模式:AI 主导提问(v1.2 提出,v1.3 由同行产品实证升级为一等交互范式)**。需求模糊时,Brain 不做"记录员",而是切换到 **Host 主导的采访模式**——像播客主持人采访嘉宾:系统先预研目标 repo,然后由 Brain 带着代码库发现的疑点/待办主动向人提问,人只需回答,任务卡/需求在一问一答中渐进成型。例:"我看报表页的 `ReportTable` 已经有分页,但没有导出。你想要的导出是给财务对账还是给用户下载?中文列名要不要?"

- 与"人下指令、AI 澄清"相比,AI 主导采访更能把人脑子里模糊的想法**逼**出来、并用代码库事实约束需求(减少 agent 跑偏)。这正是本工具区别于"语音问答"的地方:对话过程本身在产出价值。
- 实证:同行已上线产品(§9.4)整个交互就是"AI 采访人"——主界面标题即 "Podcast interview",AI 是 Host、人是 Guest。这不是我的臆想,是被验证过的范式。
- 采访深度自适应:需求清晰就一两句确认,模糊就多问几轮,但始终受"注意力预算"约束(§4.13),不没完没了。
- **采访的终止条件 = 就绪自省(§4.20)**:每轮回答末,Brain 对照项目类型的就绪清单判断"够不够开始";未就绪就朝缺口定向收敛提问(不发散),就绪就产出决策包请用户拍板"开始吗"。这把开放采访收束到明确的 go/no-go 点,防止越聊越远、偏离原始意图。
- 采访模式与"人主动派单"并存,由人决定入口:想清楚了直接说需求;没想清楚就说"我想做个 X,你问我"。

### 4.4 Agent 适配器统一接口

```typescript
interface AgentAdapter {
  start(task: TaskCard, worktree: string): Promise<RunHandle>;
  events(run: RunHandle): AsyncIterable<AgentEvent>;   // 归一化事件
  steer(run: RunHandle, instruction: string): Promise<SteerResult>;
  interrupt(run: RunHandle): Promise<void>;
  resume(run: RunHandle, message: string): Promise<RunHandle>;
  answerPermission(run: RunHandle, id: string, allow: boolean): Promise<void>;
}
```

归一化事件类型:`progress | file_changed | test_result | question | approval_request | done | failed`。

**两级集成模型(v1.4 合并强化,关键)**。合并同源方案时确认了一个此前被低估的技术事实:**headless 模式下三家的"运行中审批"能力截然不同,不能假装通用**——

- **Claude Code**:`claude -p` 对未授权操作**默认自动拒绝后继续**(不产生可等待事件)。**[warn] v1.9 一手实测纠正(来自 OctoDesk ExternalAgentBridge,§13)**:**Claude CLI 路径上 `--permission-prompt-tool` / `canUseTool` 实际不可用**,只能用其自身 `--permission-mode` / `--allowedTools`,宿主只能"审计 tool_use"而非阻塞审批。要做真正的运行中交互审批与消息注入(steer),**必须走 Agent SDK streaming input mode,而不是 CLI**。本方案 ClaudeAdapter 因此明确绑定 SDK(非 `claude -p`);若只用 CLI,则 Claude 也退化为 Tier 2(预授权 + kill_and_resume)。
- **Codex**:`codex exec` 非交互下审批策略实际退化为 `never`,强行出现审批会**挂死且无通道应答**;运行中也无法注入消息。
- **Cursor**:headless 官方路径就是预授权(`--force`/permissions 配置),无文档化的审批事件流。

因此适配层分两级,而不是强行归一:

| | **Tier 1:交互式审批**(Claude,SDK streaming) | **Tier 2:预授权 + 事后恢复**(Codex、Cursor) |
|---|---|---|
| 权限 | 保守基线 + 运行中 `canUseTool` 动态审批:越权操作阻塞在回调上 → 转 blocked 叫人 → 口头"允许/拒绝" → 进程原地继续 | 运行前一次性把沙箱权限配足;运行中不指望交互审批,越界即失败 |
| steer/改需求 | 原生:流式输入注入新消息,进程不退出 | `kill_and_resume`:SIGTERM(等当前事件边界,超时强杀)→ `resume <session_id>` + 新指令续接 |
| agent 提问 | `AskUserQuestion` / `canUseTool` 事件 | 由最终消息解析(结构化输出约定 `blocked_reason`)+ 空转超时兜底 |

**三种恢复语义**(状态机联动,务必区分):`answer_permission`(仅 Tier 1,进程不退出、原地继续)、`kill_and_resume`(通用,进程退出后带新指令续接——各家 resume 保留完整上下文;续接指令模板强制先 `git status` 自查再干)、`cancel`(放弃,worktree 保留供事后检查)。

含义:派给 Codex/Cursor 的任务必须在任务卡里把决策交代得更全(它们运行中不会问);`agent: auto` 把"需求含糊、可能要来回问"的任务优先派给 Claude(Tier 1 闭环最完整)。不点名时默认 Claude Code。

### 4.5 事件流 → 口播摘要(摘要器)

一次 30 分钟的 agent run 会产生几百条事件、几万 token 的 diff。**任何时候都不把原始流塞给语音大脑**(无论级联的文本 LLM 还是 S2S 模型——贵、装不下、也没人想听)。

摘要器分两级工作,避免"省了语音的钱却在摘要上烧钱":

- **规则级(免费,实时)**:文件改动数、测试通过率、当前在做的步骤名,直接从归一化事件里数出来,支撑 `get_status` 的即时应答;
- **模型级(廉价文本模型,惰性)**:仅在关键节点(done/failed/blocked)或人主动要求时,才把事件流的窗口喂给模型生成叙事稿。

三层产物,存 SQLite:

1. **one_liner**:"改了 5 个文件,测试 12/12 过,有 1 个待确认决策"——回叫播报用;
2. **walkthrough**:150 字口语稿,讲做了什么、怎么验证的——人说"讲讲"时用;
3. **decisions[]**:agent 自主做出的、人可能想推翻的决策清单("日期格式选了 ISO 8601")——这是语音交互里最有价值的部分。

diff 本体、完整日志永远走 `open_on_screen` 到编辑器/浏览器。

### 4.6 回叫策略引擎

```
事件优先级:  blocked(agent 卡住等人) > failed > approval_request
            > done > progress(默认不通知)

通知升级链:  控制台在线且系统空闲<5分钟 → 语音回叫(重建会话,Brain 播报)
            30 秒无应答 / 控制台离线 → 桌面通知 + ntfy 手机推送
            仍无应答且事件为 blocked → 电话(P1,可选开启)

免打扰:     静音窗口(如 23:00-08:00)内只推送不出声;
            blocked/failed 事件在静音窗口结束后立即补叫
```

人的应答方式:语音回叫场景直接开口说话(会话已在线);其余场景点击桌面通知或手机推送,控制台自动建会话。挂起状态下"对空气喊话"默认无效——可选开启**在线待命**模式:控制台页面用浏览器内 WASM VAD/唤醒词本地监听(音频不出本机、零 API 成本),检测到呼叫再重建会话。

**音频输出仲裁(v1.4 合并补强)**。多路声音会抢扬声器,需一个全局输出协调器:① 语音会话进行中时,新到的完成播报**不插播**,排队到会话收尾时带一句"另外,任务 A 也好了";② 检测到麦克风/音频设备被其他 App 占用(CoreAudio 可查,典型是 Zoom 开会)时**跳过语音播报**,直接降级走桌面/手机通知——避免完工播报打断你正在开的会。

### 4.7 审批与安全(风险分级)

语音是弱认证通道(在场任何人都能说话)且 ASR 有误听率,因此**审批权按风险分级,语音只能批到 L2**:

| 级别 | 例子 | 审批方式 |
|---|---|---|
| L0 读 | 读代码、跑只读命令 | 自动放行 |
| L1 写(worktree 内) | 改代码、跑测试、本地 commit | 自动放行 |
| L2 出圈但可逆 | 装依赖、创建远程分支、push 到自己的 feature 分支 | 语音确认("要装 lodash,可以吗?") |
| L3 不可逆/外部影响 | force push、合并到 main、部署、花钱、删数据、发消息给别人 | **必须屏幕确认**(控制台卡片点击),语音不可批 |

底座:agent 默认跑在最小权限——Codex 用内置 OS 沙箱(可硬禁网);Claude 用 `canUseTool` + allowedTools 白名单;Cursor 用 hooks + permissions 配置。**诚实声明**:Claude/Cursor 的本地限制是策略级(拦截已知工具调用),不是 OS 级硬隔离;`curl` 这类命令靠白名单挡,而非网络栈隔离。对不信任的任务,提供可选加固:把适配器进程放进容器或 macOS `sandbox-exec` 再跑。P0 接受策略级 + worktree 隔离作为默认。`--yolo` / `--force` / `--dangerously-skip-permissions` 一律禁止裸机使用,只允许出现在容器内。

**verify 命令白名单(v1.4 合并补强,安全硬伤)**。编排器会在 worktree 里跑"验证命令"(测试/构建/lint)来独立核实 agent 是否真做完。但**绝不能让语音大脑从口语自由拼装命令再以用户权限裸跑**——ASR 误听或模型幻觉即可注入危险命令(如 `rm -rf`),这是一条绕过一切沙箱的命令注入通道。规定:verify 只能从项目**预登记的命令模板**里选(`package.json` scripts / justfile 目标 / `voiceloop.toml` 登记条目),大脑只能选模板、不能自由拼装;执行时套用与 agent 同级的沙箱;规格确认时把将要执行的 verify 命令原文以**文字**推送到通知渠道留痕。用户临时口头说的"顺便看看构建时间"这类不在白名单的命令一律拒绝,引导为"那属于 agent 沙箱内的活"。

**危险操作:L3 必须强认证,复述短语不作独立因子(v1.14 修正,Codex 指出原设计安全矛盾)**。此前写"L3 靠复述特定短语对冲弱认证"——这是错的:同一麦克风、同一 ASR、同一 speaker context 的复述**不提供独立认证因子**(录音、旁人、合成语音、错误指代都绕得过),口述 PIN 还会把 secret 暴露给音频链和转写。修正:L3 操作(force push、合并 main、部署、删数据、发外部消息等)**必须由已认证屏幕点击 / OS 生物识别 / passkey 授权**(NIST SP 800-63B 也不允许把声纹当认证);**语音只能"导航到审批卡 + 朗读将发生什么 + 记录用户在场知情",绝不单独放行 L3**。复述短语可作为"用户确实听到并在场"的辅助留痕,但不是授权凭证。

**远程通道认证(v1.4 合并补强)**。电话/手机推送回复默认**只读**(听汇报、看摘要);要通过远程通道下发指令(如"继续改")必须口述 PIN 或点推送里的确认按钮——防止别人拿起你的手机就能指挥你的 agent。

### 4.8 并发、隔离与失控防护(v1.4 合并强化)

- 每个任务一个 **git worktree**(`.voiceloop/worktrees/T-xxxx`,分支 `vl/T-xxxx-slug`),互不踩踏,主工作区永远不被 agent 碰。
- worktree 的隐性成本:依赖要重装(node_modules 等不随 worktree 走)。每个仓库注册一个 `setup` 命令(如 `pnpm install --prefer-offline`),建 worktree 后自动执行;装不动的重型仓库可在配置里降级为"单 worktree 复用、任务强制串行"。
- 同一仓库的任务默认串行(一个队列);不同仓库可并行。

**任务三熔断(合并补强,防无人值守烧钱)**。"15 分钟无事件"只能抓住挂死,抓不住"活跃地兜圈烧钱"(反复改-测-改、反复重试失败命令,几小时不停)。每任务三道熔断:**墙钟上限**(默认 45 分钟)、**回合数上限**(Claude 直接用 `--max-turns`,其余按事件计数)、可选 **token/成本上限**。任一触发 → cancel → 带上下文进 blocked 叫人裁决。这把无人值守期间的失控上限变成可配置常数。

**[warn] 45 分钟单任务墙钟 ≠ 隔夜工作(v1.14 修正,Codex 指出的矛盾)**。§4.21 的"隔夜交活"不能靠一个 8 小时的超长单 run 实现——那与 45 分钟墙钟直接冲突,且长单 run 不可恢复、易失控。正确形态是**两层**:单个 attempt 仍保留 45 分钟 backstop;**上层是一个带 deadline 的 workflow**(总时长/总成本/最大 attempts/最大无进展次数),它把大任务切成 step、每个 step 边界做 durable checkpoint、失败按类型重派(transient 自动重试 / deterministic failure 禁止盲重试 / ambiguous effect 先对账)、deadline 前预留 review 预算。**这层 workflow executor 正是 Hopper 的 M3d 未实现部分**——所以在它就绪前,"隔夜交活"应诚实表述为"离席后台执行到某个 review 点",而不是"关机/合盖后连续跑 8 小时"。dispatch 前还要做 **delivery preflight**(电源/睡眠/网络/磁盘/额度/CLI 登录/secret/仓库状态/回调通道),把会导致夜间早停的问题在你离开前就暴露,而不是凌晨 1 点才回叫。

**启动对账(合并补强,防孤儿进程)**。daemon 崩溃/升级重启会杀死或孤儿化子进程。启动时扫描 SQLite:状态为 `running` 但 PID 不存在的任务 → 标记 `interrupted` → 用各家 resume 机制恢复(`native_session_id`),恢复不了则降级叫人。配合任务运行期持有电源断言(`caffeinate -i`)防 App Nap/睡眠挂起子进程(合盖场景要求插电,见 §7)。

**合并不是终点,冲突是常态(合并补强)**。原方案"完成即停在 review、由人合并"低估了并行任务 + main 前进导致的冲突。完整收尾状态机:`review`(人验收)→ 人说合并 → `merging`(先 rebase/merge main、**重跑 verify**,再合并)→ 成功 `done` / 冲突或验证失败 `merge_failed`。`merge_failed` 有明确去处:`kill_and_resume` 让 agent 解冲突,或降级为**开 PR 移交人工**。合并动作本身属 L3,永远由人触发。

### 4.9 中途插话与改需求

场景:"停一下,导出改成 Excel 格式而不是 CSV。"

1. Brain 调 `steer_task(T-0042, "...")`;
2. daemon 判断变更等级:**微调**(同一目标内的修正)→ Tier 1 走 `steer`(流式注入);**目标变更**(验收标准变了)→ Brain 提议改任务卡并复述,确认后走 `kill_and_resume`(§4.4)+ 更新任务卡;
3. Codex/Cursor 任务的 steer 处理(v1.14 更新):**官方能力已变**——Codex `app-server` 协议已支持 `turn/steer`(不打断当前轮追加输入,带 `expectedTurnId` 防 stale)、`turn/interrupt`、`thread/resume|fork`;Claude Agent SDK 的 streaming input mode 也支持运行中注入/中断/审批。所以"Codex 不能 steer"这个假设**已过时**。但要注意"**官方协议支持**"≠"**执行后端已接入**":若下游走 Hopper,其当前 runner 是 `codex exec` 一次性 adapter(见 §15/借鉴评估),真正的 mid-turn steer 需要 Hopper 升级到 app-server/SDK 流式(属其 M3b);在那之前实际仍是 `kill_and_resume` 降级,Brain 会如实提醒"正在跑的这一轮会作废"。**能力按运行时探测,不按模型名假设。**

### 4.10 数据模型(SQLite)

```
projects(id, title, type, status, repo?, created_at, updated_at)          # v1.5:coding/planning/research/...
sessions(id, project_id, started_at, ended_at, transcript_path, summary)

```

- `native_session_id` 是恢复能力的钥匙:Claude 的 session_id / Codex 的 session id / Cursor 的 agentId 都存这里,daemon 重启后仍可 `resume`。

### 4.11 多任务/多 agent 协作:共享黑板,不做 agent 间对话(v1.2 新增)

一旦 P1 支持多任务并行、甚至一个大任务拆给多个 agent,最容易踩的坑是让 agent 互相"对话"协调。**明确设计红线:agent 之间不直接通讯,只通过共享的、带主题线索的存储交换信息(黑板 / 邮件列表模型)。**

理由(吸收自外部实践者的踩坑经验):当前大模型的对话行为是"对齐给人"的——它们被训练得很"听话、很给面子"。让两个 agent 直接对话,会出现"你说得对→我也觉得你说得对"式的互相附和、绕圈子、不收敛,而且大量通讯会分散各自的注意力(见 §4.13)。

落地:

- 本方案已有的**事件总线(JSONL)+ SQLite** 就是黑板的雏形,v1.2 将其显式化为"共享上下文":每个 agent 只读写自己那份任务的记录,产出(结论、改动、决策)以**结构化、可检索、带任务/主题标签**的条目落盘,类似邮件/newsgroup 的"发帖—订阅",而非点对点 RPC。
- 需要"A 的产出喂给 B"时,由**编排器(daemon)**从黑板取 A 的结构化产出、整理成干净的上下文,再作为 B 的任务卡输入——中间隔一层人为设计的、无附和倾向的传递,而不是让 A、B 直接聊。
- 跨 agent 的协调决策(要不要合并两个分支的改动等)一律**上浮给人**语音确认,不让 agent 自主协商。

### 4.12 主动巡检模式(v1.2 新增,P2)

被动派单之外,增加一个可选的**主动模式**:daemon 定期(或在 idle 时)对注册的 repo 跑只读巡检——扫 TODO/FIXME、失败的 CI、lint 告警、过期依赖、明显的技术债,生成**草稿态任务卡**入队但不执行。下次语音回叫或用户开麦时,Brain 顺带说一句:"我巡检发现三件可以做的:补上 auth 模块的测试、升级两个有安全告警的依赖、清掉五个 TODO。要派哪个?" 人只需口头点选批准(等价于"点击审核通过"),系统即派发。

这把工具从"人想起来才用"变成"系统主动挖需求、人做决策"。安全边界:巡检只读、只产草稿;任何执行仍走正常的任务卡确认与 §4.7 审批分级,主动模式不自动提权。

实证参考(§9.4):同行的巡检系统产出的待办是**绑定具体 project、且非常具体可执行**的——例如一条"复审:官网仍无 gallery 路由与公开作品页"直接挂在某项目下,作者只需点"审核通过"就派工。这印证了主动巡检的形态:草稿任务卡要具体到"哪个项目、缺什么、建议做什么",而不是泛泛的"代码质量待提升";人一句"批准"即可转正式任务。

### 4.13 注意力预算原则(v1.2 新增,横切)

"做系统设计一定要考虑注意力"——这条对**人和模型两侧**都适用,且和本方案原有的成本/摘要设计同源,提为显式原则:

- **人的注意力**:回叫要值得打扰(§4.6 优先级)、口播要短(§4.5 三层摘要)、采访不啰嗦(§4.3)。默认不打扰,一次说清。
- **模型的注意力**:Realtime 会话只装决策相关的 Context Pack,不灌原始事件流(§4.5);单个 agent 任务聚焦、避免多跳与 agent 间通讯(§4.11);Context 预研的产出是"提炼过的概览"而非整库塞进去。
- 一句话:**每多占用一分人或模型的注意力,都要有明确回报**,否则砍掉。

### 4.14 显式轮次边界:VAD 之外的"说完了"信号(v1.3 新增,实证驱动)

原方案(§2.1)依赖 Realtime 的服务端 VAD 自动判断"人说完没有"。但中文口语 + 英文标识符混说、加上思考停顿,VAD 容易**误断**(人还在想,系统抢答)或**漏断**。因此增加一个**显式轮次边界**的交互选项:人说完按一下"说完了"(Done speaking)再发送,并可"重听"(Listen again)上一个问题。

- 两种模式并存:默认 VAD 自动轮替(手最闲);嘈杂环境/复杂需求/长思考时切"显式确认"模式(最稳,零误触发)。
- 实证:同行产品(§9.4)采用的正是显式模式——"Host 问完自动开始监听,你说完点 Done speaking 发送"。它用按钮换取了轮替的确定性,规避了本方案 §7 里"ASR 误断"这条风险。
- 落地成本极低(控制台一个按钮 + 一个热键),P0 就该带上,作为 VAD 的兜底。

### 4.15 产出沉淀与导出:不止代码 diff(v1.3 新增,实证驱动)

采访/脑暴阶段本身会产出高价值信息——澄清出的需求、被否掉的方案、agent 自主做的决策(decisions[])、预研得到的代码库理解。这些不该聊完就蒸发。新增**沉淀层**:

- 每个任务/会话可导出一份结构化产物:需求文档(采访结论)+ 决策记录 + 变更摘要 + 相关文件清单,Markdown 落盘到 repo 的 `.voiceloop/notes/`。
- 预研素材进入可复用的 **Library**(下次聊同一 repo 直接命中,省一次预研)。
- 实证:同行产品(§9.4)面板里就有 **Library(素材库)** 与 **Export(导出)**,且其作者明说"脑暴后可以快速产出高价值内容和观点"。这把工具从"派代码的嘴替"扩展成"需求与决策的沉淀器",价值面更宽。
- 边界:P0 只做最简单的"会话结束导出一份 Markdown 笔记";Library 复用与检索留 P1。v1.5 起本节被 §4.18 的统一产物库收编(从"结束导出"升级为"全程产物库")。

### 4.16 项目类型与产物模型(v1.5 新增,场景驱动)

此前版本把"任务卡 → 改代码 → diff/测试/PR"当成唯一路径。三个目标场景(`scenarios/`)证明这是过窄的假设。v1.5 引入两层抽象:

**项目(Project)> 阶段(Phase)> 任务/产物(Task/Artifact)**。一个项目有类型,决定它的产出物形态与验收方式:

| 项目类型 | 典型产出物 | 执行手段 | 验收标准 |
|---|---|---|---|
| `coding` | 代码改动 / PR | coding agent + worktree | verify(测试/构建/lint)通过 + 人验收 |
| `planning` | PRD / 架构 / 任务分解 / 里程碑(见 §4.17) | 文本模型 + 调研 agent | 文档自洽、可开工,人(常为非技术)审阅通过 |
| `research` | 调研报告 + 资料库 | 调研 agent / RFWG 类 skill / 联网检索 | 内容扎实、来源可靠,人评审通过 |
| `content/marketing` | 方案 / 内容 / 计划 | 生成 + 迭代 | 质量与目标契合,人评审通过 |
| `general` | 任务计划 + 各类产物(如**设计方案**、**谈大客户的谈判准备包/策略**) | 通用 agent 能力 | 按项目自定义验收 |

**关键设计原则:worktree / verify 测试 / PR / MERGING 是 `coding` 类型的具体实现,不是全局机制。** 前文 §4.4/§4.7/§4.8 的编码相关设计全部归属 `coding` 类型;其它类型有各自的执行器与验收器,但共享同一套上游(采访、Context 预研、回叫、摘要、审批分级、产物库)与调度骨架(项目/阶段/任务状态机)。适配层相应扩展:除三家 coding agent 外,可挂"调研/通用"执行器(它们本身也能写文档做调研,只是产出与验收形态不同)。

**项目类型模板(v1.8 强化,用户想法 B):是"类/框架",不是固定 workflow。** 预制多套模板(开发/调研/营销/…),作用是让系统**开场就识别出"这是哪一类事"**,从而套用该类型的思考框架——但**不固化"一步步怎么做"**,具体路径仍由大模型按对话灵活决定。每个模板除上表的"产出物 / 执行 / 验收"外,再定义两样:

| 模板要素 | 作用 |
|---|---|
| **识别线索** | 从用户开场判断属于哪一类(意图/关键词);识别类型是 §4.20 就绪判定的前提 |
| **就绪清单(readiness checklist)** | 该类型"可以开始"前必须澄清/准备到什么程度——**每类不同**,是 §4.20 就绪自省的判定依据 |
| **Demo 形态** | 用什么向用户预览"最终会得到什么"(§4.20 决策包) |

就绪清单 + Demo 形态(示例):

- `coding`:目标 / 可验证的验收标准 / 涉及范围 / 约束 / 代码库关键部分已理解 → Demo:可点的 HTML 原型
- `research`:调研问题 / 范围与深度 / 交付形式 / 信息源可及 → Demo:报告大纲 + 一节样章
- `marketing`:目标与成功指标 / 受众 / 渠道 / 预算 / 调性 → Demo:方案一页纸 + 样例素材或落地页 mock
- `planning`:目标 / 范围 / 相关方 / 成功标准 → Demo:文档体系目录 + 关键页样张

**为什么就绪判定必须类型化**(用户想法 B 的核心):"上下文够不够、能不能开始"不是通用判断——开发项目缺验收标准就不能开工,调研项目缺信息源就没法查,营销项目缺受众就没法定调。所以必须先识别类型,才能拿对应就绪清单去做 §4.20 的决断。

### 4.17 规划产出阶段与非技术用户(v1.5 新增,场景 2 驱动)

场景 2(非技术负责人先出一整套开工文档再实施)要求把**规划/文档产出**作为先于实施的一等阶段,而非直接对话→改代码。

**阶段流水**:`对话脑暴 → 深度采访 → 边聊边调研 → 产出文档体系 → 协同审阅(多轮修订) → 批准 → 拆解为任务批量派单 → 实施`。

- **文档体系是结构化、版本化的产物**(PRD / 架构 / 任务分解 / 里程碑 / 开工检查单),落产物库(§4.18),可在屏幕协同审阅、语音提意见、逐版留痕。
- **文档 → 任务的桥**:批准后由文本模型把任务分解拆成一批 `coding`(或其它类型)任务卡,进入 §4 的执行闭环,多任务并行/排队(§4.8)。
- **非技术用户适配**:
  - 验收基于**文档/业务**而非 diff/测试——回叫时讲"做出来的东西对不对",而非"测试过没过";要看细节走 `open_on_screen` 看渲染结果/demo,不强迫看代码。
  - 审批用**业务语言**复述(§4.7 的风险分级不变,但 L2/L3 的话术从"要装 lodash 吗"变成"这个改动会多花两天,继续吗")。
  - 采访更深、更主导(§4.3),因为要产出完整文档,澄清必须充分。

### 4.18 统一产物库(Artifact Store,v1.5 新增,横切持久化)

直接回应"全过程新产物(生成的 + 调研的)是否都持久化、能否随时召回续用"。此前持久化是零散的(events/JSONL、§4.15 结束导出、§4.1 预研 Library、§4.5 摘要各存各的)。v1.5 收敛为**一个贯穿全程的产物库**——它就是 §4.19 记忆架构里的 **L2 累积对话知识**层的存储实现;被提炼后进入 L1 知识底座。

**每个产物一条记录**:`id / project_id / type(doc|prd|architecture|plan|research-material|dataset|decision|code-diff|report|transcript…) / source(对话生成|agent产出|调研抓取|用户上传) / version / tags / body或文件指针 / created_at / created_by`。

**关键能力**:

1. **全程写入,不是结束才存**:对话里生成一版方案立即落库、调研抓到资料立即落库、agent 产出实时归档;
2. **版本化**:同一逻辑产物(如架构 v1→v2→v3)留全部版本,可对比;
3. **可检索 + 可召回注入 Context Pack**:与 §4.1 打通——新会话开场注入"本项目产物索引",AI 能主动说"我们有一版架构在这",用户也能语音点名调取("上次那版定价调研再给我看看");
4. **控制台可浏览**:产物时间线 + 版本对比;
5. **统一记忆层**:收编 §4.1 预研 Library、§4.5 摘要、§4.15 沉淀导出、事件流,不再各存各的;
6. **隐私边界**:产物可能含敏感信息(调研到的第三方资料、业务机密),默认本地存储、不外泄;导出需显式动作。

这是让场景 2、3 成立的地基:文档、调研资料、方案本身都是"产物",必须全程可存、可查、可召回。

### 4.19 上下文与记忆架构(v1.6 新增,核心统领)

**这是本方案区别于"ChatGPT 新窗口语音版"的根本。** 一个项目必须是**有记忆的**:记忆分层、持久、且随对话生长。区分两个此前被混为一谈的概念——**持久知识库**(以后所有对话都用得到,大、稳定)与**每次拼接的 Context Pack**(单次会话临时传入,小)。用户的原话精准点破:"这个上下文指的是以后所有对话可以用到的,而不是每次提问时传的。" 本节统领 §4.1(会话生命周期)、§4.18(产物库)、§4.10(数据模型)。设计记录与开放问题见 `scenarios/cross-cutting-context-memory.md`。

**① 分层记忆模型(Memory Tiers)**

| 层 | 名称 | 存储 | 生命周期 | 内容 |
|---|---|---|---|---|
| L0 | 用户档案 | `~/.voiceloop/profile.md` | 跨项目、长期 | 偏好、常用技术栈、编码/沟通风格、术语热词 |
| L1 | 项目知识底座 | `<repo>/.voiceloop/knowledge/` | 项目级、长期稳定 | 目标/背景/约束、代码库理解(架构/模块/术语)、关键决策、领域知识、文档体系 |
| L2 | 累积对话知识 | 产物库 `artifacts`(§4.18) | 项目级、随对话增长 | 每次对话新生成的方案/决策、新调研的资料 |
| L3 | 会话工作记忆 | Context Window + 转写 | 单次会话 | 最近 N 轮、当前任务 |

**Context Pack(§4.1)= 检索器从 L0+L1+L2 挑相关的 + L3,拼进 Window**。知识库(L0/L1/L2)是持久大底座,Context Pack 是每次临时取用的小切片——两者不是一回事。

**② 项目奠基:先备后答,且持续深化(v1.7 按用户决策定稿)**

- **首次奠基是阻塞式的"先备后答"**:全新项目首次对话,系统先把知识底座建到"足够"才进入实质问答——宁可让用户等,也不空脑袋硬答(用户明确选择:首轮质量优先于即时响应)。产出持久化 L1(coding:扫代码库出架构/模块/术语/约定;planning/research:立目标/背景/领域调研),形态是人类可读本地文件 + 检索索引,一次建成长期复用。
- **奠基不是一次性的,是按需持续深化**:对话过程中,若系统判断当前 context 不足以给出有价值的回答,它有权**暂停回答、先去补充背景知识**,并告知用户"这个我得先补点背景,稍等"。补充内容可能**超出当次提问的直接范围**——是在为这个项目和后续可能的提问前瞻性攒料,因此看起来和当次问题不完全相关,这是被允许且鼓励的。
- **透明的「学习中」状态(关键,用户强调)**:积累知识的等待可能较长,必须让等待**可理解、可信赖**——控制台与语音都要表达"我在积累信息,不是卡顿":说清在学什么、进度、大概还要多久。目的有二:让用户知道为什么等;让用户感到"AI 现在懂得更多了"。这是本工具与"转圈干等"的根本区别——**等待本身是有价值且可见的**。`learning` 因此成为一等会话状态(与"对话中"/"执行中"并列)。
- **会话预热(每次,轻)**:已有项目开新对话时加载 L1 + 按话题增量准备(含代码库变更的 git diff 增量刷新)。

奠基有无,就是"有价值的持续对话"与"ChatGPT 新窗口"的分界。

**③ 三条用户路径,三种上下文装配**(用户指出的核心差异):

| 路径 | L1 状态 | 装配 |
|---|---|---|
| 全新项目 | 无 → **触发奠基** | Pack = L0 + 新建 L1 + L3 |
| 已有项目·新对话 | 已存在 → 加载 + 增量刷新 | Pack = L0 + L1 相关切片 + L2 检索 + L3 |
| 续接对话 | 已存在 | 加载该会话 L3 完整历史 + L1 + 相关 L2,无缝续接;结束时沉淀回 L2/L1 |

**④ 知识库生长闭环**(只 append 会膨胀陈旧,需闭环):生长(新产物写 L2)→ 提炼(会话末/定期把 L2 稳定重要的蒸馏进 L1,如更新 `decisions.md`)→ 失效(代码变更标记 L1 受影响部分过期,`git diff` 增量重建)→ 索引(关键词/embedding)→ **人可编辑**(L1 是本地 Markdown,人可直接改纠正 AI 理解,AI 尊重)。

**⑤ 本地文件布局**:

```
<repo>/.voiceloop/knowledge/    # L1:project.md / architecture.md / glossary.md / decisions.md / domain/ / index.json
<repo>/.voiceloop/artifacts/    # L2:方案多版本 / 调研资料 / report / diff
<repo>/.voiceloop/sessions/     # L3:各会话转写
~/.voiceloop/profile.md         # L0:用户档案(跨项目)
```

**⑥ 已确认的关键决策(v1.7,用户拍板)**:

1. **奠基时机**:先奠基完成再答(阻塞式先备后答)+ 按需持续深化 + 透明「学习中」状态(见②);
2. **什么进 L1、由谁定**:自动提炼 + 静默沉淀;但重大决策/架构变更在回叫时口头告知"这个我记下了",人可否决;
3. **L0 用户档案**:做——自动积累偏好/技术栈/术语热词,可查看、可编辑(顺带提升 ASR 专有名词准确率);
4. **知识库与 git**:默认 `gitignore` 不进仓库(不污染、不泄漏),但支持用户显式选择提交 `knowledge/` 以便团队共享;
5. **代码变更失效**:每次会话预热用 `git diff` 增量刷新受影响部分。

### 4.20 收敛与就绪决断循环(v1.8 新增,反发散)

对话默认会发散;若采访(§4.3)没有终止条件,容易越聊越远、偏离用户的原始意图。本节是**收敛器**:把开放对话主动收束到一个明确的 go/no-go 决策点。

**就绪 = 双维度充分性(v1.10,按设计哲学升级)**。此前只对照"类型模板就绪清单"(偏需求维度)。现明确就绪要**两个维度都过阈值**,对应 AI 的两类行为(见 §4.2):

1. **知识充分度**:项目奠基 + 累积/调研知识是否够支撑实施(§4.19 的 L1/L2)——这是"**准备知识**"行为的产出;
2. **需求明确度**:用户想要什么、验收标准是否够清楚(类型模板就绪清单 §4.16)——这是"**回答问题**"行为的产出。

**每轮回答结束,Brain 做一次「就绪自省」**,判断这两维"现在够不够**完美**实施":

- **未就绪** → 缺哪维补哪维:知识不够 → AI 继续**主动准备知识**并显示「学习中」(§4.19,不必用户提问);需求不够 → **定向采访**补缺口(§4.3),不发散到无关话题。
- **不过早收敛**(§4.4 哲学):聊天阶段允许发散(思路完善),只在两维**真的都够了**才收敛;收敛不是"尽早逼用户拍板下指令",而是"让用户尽情聊、AI 在背后判断火候、够了才端出方案"。
- **就绪** → 调 `propose_start` 产出一个**决策包(Decision Package)**,主动请用户拍板"要不要现在就开始":
  1. **成果预览**:完美实施后你会得到一个什么样的东西(一句话 + 要点);
  2. **实施计划**:会按哪些步骤做(`coding`=任务分解 / `research`=调研计划 / `marketing`=执行步骤;确认后即可 dispatch)。**每一步显式标注负责方:AI 执行 vs 需要人配合**(v1.12,owner 强调)——有些步骤 AI 做不了或不该独做(提供凭据/线下动作/对外拍板/找人要资源),计划里要把"人要配合什么"单列出来,而不是假装全由 AI 完成;
  3. **Demo(可能的话)**:一个轻量 HTML demo 展示"最终长什么样"(UI/产品类最有效;非 UI 类用报告样章 / 方案一页纸 / 流程图替代)。Demo 是 mock 数据的可抛弃预览,不是真实施,生成便宜;
  4. 明确一问:**"要不要现在就开始?"**

**为什么这三件套是关键**(用户强调 + v1.10 哲学):用户可能不知不觉已经把信息说够了,由 AI 帮做"可以开始了"这个决断;而【实施计划 + Demo + 成果预览】让用户**看得见**将得到什么,是比一句"我准备好了"强得多的决策依据。更深一层——它实现了**认知负担转移**:用户"思路越来越窄"的解药不是逼他把需求表达全(难),而是让他**看着具体的东西判断对/不对/调一下**(易)。确认是**审阅式(reactive)**而非**规约式(proactive)**,负担足够低,"聊到 AI 自动提议开始、用户轻点头"才成立。用户据此 go / 再改 / 补充。

**衔接**:依赖 §4.16(先识别类型才有就绪标准)、是 §4.3 采访的**终止条件**、决策包的实施计划即确认后 dispatch 的内容、成果预览与 Demo 让 §4.16 验收标准具象化。此机制对三种项目类型通用,但"就绪门槛"和"Demo 形态"按类型取(§4.16)。

### 4.21 多人 / 会议旁听模式(v1.12 新增,交互形态扩展)

此前 §1.3 把"多人会议"列为 non-goal。owner 提出一个有价值的扩展形态,故松绑为**未来交互模式**:不必总是"单人对着 AI 聊",可以把 AI **拉进一场多人电话会**(如你和客户开会),它有两种旁听姿态:

- **可打断(参与式)**:像会议里的一个成员,需要时插话补充/澄清;
- **不打断(纯旁听思考)**:全程只听只想、不出声,会议结束后**单独和你开一个小会**,把它旁听中理解到的东西汇总成决策包(成果预览 + 人机分工计划 + Demo),确认后就开工——"**明天早上起床,它交活了**"。

设计要点与边界:

- 这是 §4.19 记忆奠基 + §4.20 就绪决断在"多人输入源"上的自然延伸:会议音频是一路额外的"准备知识"输入,就绪判定与决策包机制不变。
- **权限与隐私是硬约束**(排在体验之前):多人会议涉及他人语音,录音/转写/接入需**全体知情同意**;第三方语音默认只作本地理解、不外泄;这类场景的合规门槛比单用户高,故列为**未来模式(P2+),不进 P0**。
- 技术上:纯旁听 = 一路只读 ASR 流喂给"准备知识";参与式 = 复用 barge-in/轮次机制,但要处理多说话人分离(speaker diarization)。
- **落点仍是"隔夜异步交活"**:呼应本方案的核心价值——人把虚的事聊透(哪怕是在和别人开会时),AI 后台把实的事做完,做完叫人(§4.6)。

### 4.22 部署拓扑:移动沟通端 × 桌面/服务端执行(v1.13 新增,落地形态)

**核心洞察(owner 提出)**:前脑与后端的分离不只是逻辑上的,更应是**物理跨设备**的——**沟通天然是移动的**(人随时随地想聊、在沙发上/路上/开会间隙),**执行天然是固定的**(要算力、要代码库/凭据、要长时后台跑)。所以最方便的形态是:**人在移动端随时沟通,沟通/拍板完,桌面端或服务端的生产环境直接去实施,做完把结果推回移动端。**

这把 §4.1"语音会话与开发任务生命周期解耦"、§13"语音前脑 + 执行后端分层"推到部署层面:**沟通面(前脑)与执行面(后端)是两个可以跑在不同设备上的进程**,靠一条安全通道 + 事件流连接。

**三种部署拓扑(按成熟度与场景)**:

| 拓扑 | 沟通面(前脑) | 执行面(后端) | 场景 | 分期 |
|---|---|---|---|---|
| **T1 单机本地** | 桌面浏览器控制台 | 同机 daemon + 执行后端 | 开发者在电脑前 | P0(先跑通) |
| **T2 移动沟通 + 桌面执行** | **手机**(PWA/浏览器/原生) | 家里/公司的**桌面 Mac** 常驻 daemon + 执行后端 | 人离开电脑但机器在家干活("路上聊,家里的 Mac 做") | P1(owner 重点) |
| **T3 移动沟通 + 服务端执行** | 手机 | **云端/自托管服务器**生产环境 | 团队 / 7×24 / 彻底离开个人电脑 | P2 / 愿景 |

**移动端的正确定位**:不是"把整个产品塞进手机",而是手机只做**沟通面**——语音 I/O、看 Demo/diff、拍板 go/no-go、回叫应答、审批(L2 语音、L3 屏幕点);重活(项目奠基、记忆库、agent 执行、worktree)全在执行端。这与竞品的成熟形态一致(Happy/Omnara/Cursor iOS/Nimbalyst iOS 都是"手机遥控本地 agent")。

**跨设备带来的关键设计点**:

1. **通信契约(缝合层的跨设备版)**:前脑(手机)产出的决策包/任务卡,经安全通道 drop 到执行端;执行端的事件/回叫经 transport(NotificationIntent + ntfy/push)推回手机。前脑与后端之间只传"意图 + 事件",不传大产物(diff/日志走链接回屏幕看)。
2. **安全通道(已定稿,详见 `mobile-desktop-connectivity.md`)**:T2 优先 **Tailscale 直连**(免自建);要"QR 配对 + LAN 直连"体验或 T3/过防火墙时,**照 OctoDesk Desktop Remote 的协议模板重实现瘦身版**——LAN WS 直连优先 + 自建 WS 密文中继兜底 + Noise XX E2E(服务端只见密文),配对/信任/resume/推送隐私五件套直接采用 OctoDesk 设计(重实现不 fork 代码;注意 OctoDesk 是只读面,VoiceLoop 需自定义双向 capability)。**不用 WebRTC P2P**。手机浏览器采集麦克风需 HTTPS(secure context,§3.2 已列)。远程通道下发指令需 PIN/确认(§4.7)。
3. **分层记忆的设备归属**:L1 项目知识底座 / L2 产物库 **放执行端**(离代码库近、随任务生长);L3 会话工作记忆随会话(手机);L0 用户档案可云端同步跨设备。手机不持久化大知识库,只做 I/O + 最近对话缓存。
4. **断连鲁棒性**:手机网络不稳时,前脑会话可断可重建(§4.1 会话解耦天然支持);执行在后端**不受手机断连影响**(本就异步)——这正是"隔夜交活"成立的前提:你手机没电了,家里的机器照做,醒来推给你。
5. **审批跨设备**:L2 手机语音批;L3 必须手机屏幕点卡片或复述短语(§4.7 分级不变,只是承载在移动端)。

**与 Hopper 后端的关系**:执行端 = daemon + 执行后端(§13 待确认的落地映射里首选 Hopper)。Hopper 本就是"文件系统为真相 + 事件溯源 + console(127.0.0.1 SSE watch)"的本地后端,天然适合 T1/T2;T3 需要把它跑在服务器并把 console/事件流经安全通道暴露给手机。这条与"VoiceLoop 前脑 + Hopper 后端"分层完全一致,只是把后端放到了另一台设备。

**分期建议**:P0 先 T1(同机跑通闭环,不引入跨设备复杂度);P1 做 T2(手机沟通 + 桌面执行,靠 Tailscale + 手机 PWA,这是 owner 认为"最方便"的主形态);T3 服务端执行留到有团队/多用户需求时。

## 5. 关键时序(三个核心场景)

### 5.1 派单:对话 → 任务卡 → 后台执行

```
(人点选 reporting-app → daemon 后台跑 Context 预研,Brain 拿到概览)

人: "用户下载,带表头。"
Brain: → create_task(raw_requirements, repo)  (daemon 侧文本模型起草任务卡)
Brain: "我复述一下:...验收是 Excel 直接打开不乱码。对吗?"
人: "对,派给 Claude。"
Brain: → confirm_and_dispatch(T-0042, claude)
daemon: 建 worktree(+跑 setup)→ ClaudeAdapter.start() → 事件流入库
Brain: "开工了,做完我叫你。"(不承诺时长——模型预估不可靠)
(Brain 主动 suspend_session / 45 秒空闲兜底 → WebRTC 断开,语音成本归零)
```

### 5.2 回叫:完成 → 播报 → 续聊

```
daemon: AgentRun done → 摘要器产出三层摘要 → 策略引擎:done 级
分支 A(控制台在线、有麦克风授权):
  daemon: 签发 ephemeral key → 直接重建 Realtime 会话 ← 注入上下文包
  Brain: "CSV 导出做完了,5 个文件,测试全过,有 1 个决策要确认,现在讲吗?"
  (30 秒无人应答 → 挂断,转分支 B 的通知)
分支 B(控制台离线/无应答):
  本机: 桌面通知 + ntfy 推送(文本摘要);人点开控制台 → 建会话
人: "讲。"
Brain: "日期格式我用了 ISO 8601,理由是...要改吗?"
人: "不用。开 diff 我看看。" → open_on_screen(T-0042, diff)

```

```

```

### P3(愿景):对话驱动的项目协作平台

初稿完成后做了一轮完整自审,立场是"证伪":逐节找**无法实现**、**不合理**、**自相矛盾**三类问题。结论:总体架构成立,但初稿有 2 处无法实现、4 处不合理、2 处自相矛盾/反模式,全部已在正文修订。清单如下:

| # | 位置 | 问题 | 定性 | 修订 |
|---|---|---|---|---|
| R1 | §4.1 | 初稿把"人开口"列为挂起后的建会话触发器。但挂起 = WebRTC 已断,**没有任何进程在听麦克风**,对空气说话不可能唤醒 | 无法实现 | P0 唤醒动作明确为"点击";常听改为可选的"在线待命"模式(浏览器内 WASM VAD,本地检测、音频不出本机)+ P2 唤醒词 |
| R2 | §3.2 | 手机经局域网 `http://` 访问控制台——浏览器对非 secure context 直接禁用 `getUserMedia`,麦克风根本拿不到 | 无法实现 | 手机访问强制 HTTPS(`tailscale serve` 自带证书 / mkcert),写入组件表 |
| R3 | §2.3 / 4.6 / 5.2 | 初稿回叫用 `say` 播报,人听完再手动建会话续聊——把"工具叫人对话"退化成"闹钟 + 回拨"两段式,与产品核心体验相悖 | 不合理 | 控制台在线时直接重建 Realtime 会话、Brain 亲口播报并等待接话(30 秒无应答挂断);`say` 降级为兜底。前提(页面在线、已授权、已交互)与降级路径已写明 |
| R4 | §4.2 / 4.3 | 初稿让 Realtime 语音模型直接产出结构化任务卡(goal/acceptance/constraints)。语音模型的结构化输出与指令遵循明显弱于文本旗舰模型,任务卡是全系统的契约,不能建立在最弱一环上 | 不合理(高风险) | `create_task` 只上交对话要点;任务卡由 daemon 侧强文本模型结合完整转写起草,Brain 仅复述确认。同时补充工具延迟期间的口头过渡要求 |
| R5 | §4.7 | 初稿承诺"默认无网络出口"。Claude Code / Cursor 本地运行**没有 OS 级沙箱**,只能靠工具白名单和 hooks 做策略级拦截,该承诺无法兑现 | 无法兑现的承诺 | 按适配器如实分级:Codex 沙箱可硬禁网;Claude/Cursor 为策略级,可选容器 / `sandbox-exec` 加固;P0 明示接受策略级 + worktree 隔离 |
| R6 | §4.8 | 初稿忽略 worktree 的依赖安装成本:node_modules 等不随 worktree 走,agent 进去连测试都跑不起来 | 不合理(遗漏) | 每仓库注册 setup 命令,建 worktree 后自动执行;重型仓库可配置降级为单 worktree 串行 |

| R8 | §1.1 / 5.1 | Brain 口头承诺"大概半小时"——LLM 无法可靠预估 agent 任务时长,承诺必然经常落空 | 反模式 | 话术改为"做完我叫你",禁止时长承诺 |
| R9 | §4.5 | 摘要器"增量消费全事件流"意味着任务全程持续烧摘要模型的钱,与"省 Realtime 成本"的初衷矛盾 | 自相矛盾(经济) | 两级摘要:统计走纯规则(免费、实时),叙事走模型(仅 done/failed/blocked 或人索要时惰性生成) |

### 8.1 复核后维持原判的设计(曾被质疑)

- **"真全双工"不做**:Realtime 的 VAD 轮替 + barge-in 已满足"对话感",Moshi 类全双工模型工程成熟度不足——维持。
- **浏览器承载语音而非原生 App**:WebRTC/AEC/权限全由浏览器解决,是 P0 最短路径——维持,原生留 P2。
- **Brain 无状态**:每次重连注入上下文包即可恢复"记忆",换取语音层可任意重建的鲁棒性——维持。
- **语音审批封顶 L2**:语音是弱认证通道,L3 必须屏幕点击——维持,且被 R4 强化(连任务卡都不信语音模型,遑论 force push)。

### 8.2 遗留开放问题(不阻塞实施,实施中验证)

1. Codex 无运行中提问能力,`question` 事件靠结构化输出约定上浮,agent 不一定每次遵守——需要 prompt 强约束 + 终稿解析兜底,实测调优。
2. 中文口语 + 英文标识符混说的 ASR 准确率需实测;若复述纠错轮次过多,考虑在控制台同屏显示任务卡文本辅助确认。
3. 回叫重建会话在 Safari/iOS 上的 autoplay 策略比桌面 Chrome 更严格,手机端可能只有通知链路可用——P0 手机端按通知链路验收。

### 13.2 重定位:VoiceLoop 收窄为三个增量能力,不再"从零造全栈"

据此,本方案的定位调整:**VoiceLoop 不作为独立从零实现的全栈产品**(那会重复两个项目约 80% 的工作),而重定位为上面三个增量能力的设计规格。§4 的下游部分(适配器/编排/任务流/验收/恢复/多端)标注为"**复用 OctoDesk / OpenClaw,而非自建**";本方案聚焦并深化它独有的语音层、记忆奠基层、采访决断层。

推荐的三层架构(松耦合,不合并仓库):

- **载体 = OctoDesk(千手)**:UI/多端、文件邮件知识库、ExternalAgentBridge、Work Steward、反向 MCP 安全;

融合是否落地、走哪个战略选项(A 并入千手 / B 独立但复用 / C 极薄语音遥控器 / D 各自独立)属商业取舍,归 owner;分析文档 §6 给了推荐(A)与理由。

### 13.3 必须回填的硬事实(不论是否融合)

1. **Claude CLI 无 `canUseTool`/`--permission-prompt-tool`**(OctoDesk 一手实测)——已回填 §4.4:CLI 路径靠 `--permission-mode`/`--allowedTools` + 只审计 tool_use,真交互审批得走 Agent SDK。

3. **反向 MCP 安全模型**(token+pathGateway+contentScanner+taint,fail-closed)优于 §4.7 的策略级拦截,应吸收。
4. **失败可见性**升为显式原则:intake/规划/派发失败必须有真实反馈 + 审计留痕,绝不静默吞没(尤其语音场景——失败要"说出来")。这是 OctoDesk Work Steward dogfood 的血泪教训。

### 13.4 可从两者借鉴强化本方案的清单(择要)

### 13.5 VoiceLoop 对两者的理念反哺(v1.10 补)

反过来,VoiceLoop 对两者最独特的贡献不是某个后端能力,而是**理念**:OpenClaw 的 Spec Triad 与 OctoDesk 的 draftWorkPlan 仍属"**指令翻译**"范式(用户给输入 → 系统结构化),而 VoiceLoop 主张"**对话自懂**"范式(用户只聊 → AI 沉淀规格 → 两维就绪后自动提议开始,§0/§14)。若融合,这条理念能把千手 Work Steward 的入口从"填目标/给指令"进化为"聊天到自懂"——交互层面的差异化。此外借鉴要带上边界纠错:OctoDesk 实测 **Claude CLI 无 `canUseTool`**(§13.3),Spec Triad 这类结构化产物应作为 **AI 的产物**而非**要求用户填的输入**(否则又滑回指令翻译)。

## 14. 设计哲学定基(v1.9 → v1.10)

**触发**:owner 与朋友沟通后提出项目的"两个最大背景",把此前散落各处的直觉收敛成一条第一性原理。洞察与深挖见 `scenarios/design-philosophy-conversation-over-instruction.md`。

**这次不是加功能,是给全文定一个"为什么"**:此前 v1.1–v1.9 攒了很多机制(采访、奠基、记忆、收敛、决策包),但没有一句话说清它们**共同服务于什么信念**。v1.10 补上——**对话优先于指令**(§0 三条第一性原理):指令是有损压缩、对话是逐步展开;不要求用户会下指令;AI 是高级助手不是指令翻译器。

**它带来的方向修正(重心转移,非推翻)**:

- 任务卡/spec 从"用户要费力提供的输入"→"**AI 聊天后自己沉淀的产物**"(§4.2);用户永远不必写规格。
- 就绪判定升级为**双维度充分性**:知识充分度(准备知识)AND 需求明确度(回答问题),两维都够才提议开始(§4.20)。
- AI 两类行为显式建模:**准备知识(proactive,不依赖提问)** + **回答问题(reactive)**(§4.2)。
- 认知负担从"表达需求"(难)转移到"审阅 Demo"(易);确认是审阅式而非规约式(§4.20)。
- 发散/收敛节奏明确:不过早收窄,聊够了(两维都够)才收敛(§4.4 哲学 / §4.20)。

**对生态**:这条理念是 VoiceLoop 相对 OpenClaw/OctoDesk 的核心差异——它们仍在"翻译指令",VoiceLoop 走"对话自懂"(§13.5)。

至此,前 13 章的机制有了统一的"为什么";后续实施应以这条哲学为准绳,任何"要求用户把需求说清楚才能开始"的设计都要重新审视是否违背它。

## 17. Codex 对抗性 review 的结构性发现(v1.13 → v1.14)

**来源**:4 个 Codex 会话(gpt-5.6-sol / reasoning max)分角度深挖,完整报告在 `codex-findings/`(01 架构红队 / 02 Hopper 集成 / 03 语音记忆〔仍在跑〕/ 04 交互产品)。它读了方案 + Hopper 源码 + 联网核实官方文档。**总判定:战略方向 Conditional Go,但"按当前方案直接做完整产品"是 No-Go——应先做一个窄闭环验证最脆弱的假设。** 已把可直接落地的事实纠正回填到 §4.1/§4.7/§4.8/§4.9/§7;以下是需要作为设计约束长期记住的结构性发现。

### 17.1 最危险的是"相关错误链",不是单点故障

Codex 指出本方案最大风险:**让同一个 Brain 产事实、判缺口、做 Demo、再自评"够不够完美实施",这些错误高度相关而非相互校验**。错误链:`错误/被投毒的奠基 → Context Pack 召回 → Brain 按错事实采访 → 同一 Brain 判 ready → 同一 Brain 生成看似合理的 Demo → 用户因具体预览产生自动化偏信 → 轻量"好" → 无人值守执行`。Demo 和轻确认在这条链上**不是天然护栏**(依赖同一错误事实会放大说服力)。**真正独立的护栏必须换信息源或换判定机制**:机械事实检查、独立模型/规则 evaluator、版本化 acceptance contract、OS sandbox、独立 verifier、高风险点人工签署。→ 设计约束:readiness 判定必须与生成/执行**解耦**(独立 evaluator 只读证据、不读 Brain 的自辩)。

### 17.2 就绪判定必须可校准,否则"双维就绪"只是装饰(§4.20 升级方向)

Codex(01+04)一致:当前"知识充分 + 需求明确"两维**太粗、无量表、无 ground truth、无校准**。升级方向:① 拆成**四维**——知识充分、需求明确、**可执行性**(环境/权限/依赖/预算)、**可验证性**(有没有验收 oracle);② 每维是"证据账本"(每条 claim 带 state/来源/置信度/错误影响/是否 critical),不是模型自报分数;③ **硬门槛**:任一 critical 项 unknown/conflicting 直接失败,不能被一堆低权重已知项平均掉;④ 加一个独立的 `P(material_rework)` 预测 + `NetVOI`(再问一个问题是否值得);⑤ 先 **shadow mode** 记录、人工标注,积累 false-ready/ECE/Brier/返工率后再按项目类型和风险层校准阈值。"perfectly implement"是错误的停止条件(奖励无止境追问),应改为"剩余不确定性低于本次风险预算,且再问的预期收益<用户负担"。

### 17.3 就绪 ≠ 授权:两把钥匙必须分开(§4.7 强化)

Codex(04):用户不反感 AI 有主见,反感的是**边界不清**。必须把**认识判断(Epistemic key:证据够了)**和**治理授权(Authority key:有权的人批准了这个 package+scope+副作用+预算+有效期)**拆成两个独立字段/状态转换。多人会议"大家听起来都同意"不能代替 Authority key——授权者身份本身是 critical requirement。轻确认按风险渐进(R0 自动 / R1 一次确认+可撤销 / R2 显示 exact diff / R3 强认证),授权 token 绑 package hash+环境+预算+外部对象+有效期;执行中发现新 scope 或 critical 假设错误就暂停给 Plan Delta。

### 17.4 记忆首先是安全边界,其次才是体验(§4.19 的 G1 升级为 P0 安全项)

Codex(01):L0-L3 持久记忆的头号问题不是陈旧/膨胀,而是 **provenance + poisoning + 跨项目泄漏**——仓库/网页/上传资料/会议参与者都能污染候选记忆,当前"自动提炼+静默沉淀"会把一次 prompt injection 固化成未来项目的行动依据(2026 多篇 memory-poisoning 研究直接命中)。修正:记忆写路径改为 `raw evidence(不可信) → candidate(带来源/quote/trust/expiry) → 冲突/taint/policy 检查 → 只有低影响项目本地事实自动入库,偏好/决策/外部事实需人或 reviewer 批准 → trusted`;**L0 硬规则:第三方内容永远不能定义"用户喜欢什么/允许什么/凭据在哪"**;检索期做 taint 过滤,删除要传播(连带 embedding/摘要/提炼/备份)。

### 17.5 VoiceLoop × Hopper:边界对但成熟度被高估,必须先立唯一所有权(§13 强化)

Codex(01+02):`business-flows.md §11` 的前后端切分**方向正确,但把 Hopper 的流式事件/运行中 steer/DecisionRequest runtime/NotificationIntent transport/workflow executor 当成可直接复用是最现实的交付断层**——这些目前**只有 schema、没有运行时**(属 Hopper M3b/M3c/M3d/WS4)。所谓"薄缝合层"实际是一套控制平面(durable outbox、命令服务、事件游标、审批收据、幂等/对账、runtime adapter、通知 transport)。**必须先立唯一所有权矩阵**(task status/approval/budget/retry/notification 各只能有一个 owner,否则 split-brain),用 durable 协议(`DispatchEnvelope` + 事件 cursor + idempotency)连接,而不是共用 SQLite/JSONL 或让 VoiceLoop 直接改 Hopper 内部状态。**行动建议:owner 一旦选 VoiceLoop+Hopper,先出 ADR 明确 supersede 哪些章节(尤其 §4.10 数据模型)+ owner matrix,再写代码**——否则工程师会同时实现旧 daemon 和新 bridge。

### 17.6 好消息:窄闭环今天就能拼出(§6 P0 的落地路径)

Codex(02):**不改 Hopper 源码,VoiceLoop 侧写四块胶水(task-card renderer / CLI client / 只读 event bridge / durable callback outbox),3–4 工程日可跑通** "语音拍板 → drop 进 Hopper → 跑到 review → 消费完成事件 → 一次语音回叫"。**唯一红线:PoC 产品语义必须是"执行和闸门已结束、等待验收",不能说"任务已完成"**(Hopper code task 要 merge 后才是 done);且不能把电话里一句"好"直接转成 `review approve`+merge。它给了完整的 PoC 步骤、字段映射、事件消费协议(文件 polling + cursor/gap 处理)和 8 条验收标准(重放幂等、bridge 重启只回叫一次、verification fail 报"闸门阻断"而非"完成"等)。

### 17.7 其它已回填的事实纠正

- **成本**:S2S 比级联贵约 5–6×(非一个数量级),mini S2S 可能接近级联;连接不收费、静默不计费;真实大头是 foundation/agent/verify/retry(已改 §4.1/§7)。
- **Codex steer**:官方 app-server 已支持 `turn/steer`,"不能 steer"过时;但要按运行时探测(已改 §4.9)。
- **L3 复述短语**:不是独立认证因子,L3 必须强认证(已改 §4.7)。
- **隔夜交活 vs 45 分钟墙钟**:需 deadline workflow 两层结构,非超长单 run(已改 §4.8)。
- **新识别的 P0 缺口**:身份/多说话人认证、跨边界事务幂等(outbox/inbox)、独立 acceptance oracle、secret/egress/供应链隔离、canonical intent/ASR 审计、数据删除/同意传播——均记入待办,实施前需覆盖。

### 17.8 语音层与记忆层技术核实(03 会话,已完成)

**语音(§2.1 更新方向)**:① "默认级联"结论**仍成立但理由要改**——2026 价格下级联不再"便宜一个数量级"(S2S mini 甚至接近级联,Gemini 3.1 Flash Live 标价很低);级联真正的优势是**文本中间态可检查 + 工具参数可用 Structured Outputs 约束 + 可精确保存"用户听到了什么" + 每段可本地化**。关键事实:**GPT-Realtime 系列不支持 Structured Outputs**——"能 function-calling"≠"工具参数足够可靠",τ-Voice 论文显示原生语音 agent 任务成功率(31–51%)远低于文本(85%)。所以正确架构是 **S2S 只做"对话呈现层"(听/说/打断/复述),一旦要写文件/精确参数/审批/长任务就把 turn 交给文本 agent**——这也是 GPT-Live 官方方向。② **打断要截断"已听到的历史"而非仅 cancel**:必须维护 playout watermark,未播放的文本标 `unheard`、不进对话事实(否则会产生"幻觉历史")——LiveKit Agents 原生支持这个,是选框架的关键 spike 点。③ **turn 检测要分三层**(VAD / 语义 EOU / 打断策略),只用 VAD+固定静音会在中文停顿和英文标识符处频繁抢答。④ **浏览器 AEC 够做 P0 基线、不够做质量承诺**(USB/蓝牙切换、double-talk、TTS 走独立播放路径都会破功),必须留耳机/PTT 降级 + 原生 VoiceProcessingIO(P1)。⑤ **中英混说必须自建 300–500 条 golden 回归集**(仓库名/符号/CLI flag/数字),用单语 WER 代替不了。⑥ Apple Silicon 本地:**faster-whisper 在 Mac 走 CPU 不是 Metal**,本地 STT 该用 MLX 路径(MLX Whisper / Qwen3-ASR)、TTS 用 Kokoro MLX(需预热)。

**记忆(§4.19 更新方向)**:记忆生命周期**不能只是"后台摘要 + git diff 刷新"**,P0 应自建**可重放的 append-only 记忆事件账本**,派生当前视图和 `.voiceloop/knowledge/` 文档;`decay` 只影响排序不代表失效,`invalidate` 要可逆留证,合规 `forget` 要从 FTS/向量/缓存/备份真正清除;**代码事实的权威源是本地文件 + Git(source hash/ancestry),LLM 只能提名 consolidation/失效候选**。可 PoC 借鉴:Hindsight(shadow)、Letta MemFS、Graphiti 双时间、LangMem 后台 consolidation;检索 P0 用 **SQLite FTS5 + `rg` + provenance**,概念召回再叠 sqlite-vec。

**会话挂起/重建**:60 分钟(OpenAI)/15 分钟(Gemini)会话上限是**必须架构绕开的供应商边界,不是产品目标**;要持久化四类状态(AudioSession 可丢 / ConversationState / TaskState / MemoryState 不可丢),重建时注入 **1.5k–3k token 的小 Context Pack(带版本,校验 HEAD/task version 失配则重取)**;45 秒 idle 阈值改为实验参数(连接空闲成本 vs 重建首响 vs 回返率分桶)。

完整证据与选型见 `codex-findings/03-voice-memory-tech.md`。
