# 01 · 设计与分布

## 1. 设计目标

600 条素材服务潜在客户访谈准备、产品能力盘点、对话测试设计和 RAG/记忆治理回放。每条只描述一个主情境，但可以包含多个关联动作；若一句话实际要求拆成多任务，问题本身保留这种自然表达，用于测试系统是否先分组确认而不是直接并发派发。

本目录是“场景层”素材，不宣称已经具备完整多轮 transcript、授权状态和验收 oracle。自动评测需要在选定子集上另补执行 fixture。

## 2. 单条记录结构

每条表格行包含：

| 字段 | 含义 |
|---|---|
| `ID` | 领域前缀加三位序号，全语料唯一 |
| `需求频率先验` | `H` 高频、`M` 中频、`L` 长尾；是领域内启发式先验，不是实测概率 |
| `角色与情境` | 谁在什么生产力场合提出问题 |
| `潜在客户提问` | 尽量保留自然口语、指代、省略、犹豫或约束冲突 |
| `对应目的` | 用户真正想改善的结果或减少的成本 |
| `档位` | 复杂度、首个可审阅结果时延、现实周期、交互轮次、工具深度、安全风险 |
| `必需工具族` | 完成当前问题确需的唯一工具族；不代表当前已原生连接 |
| `上下文模式` | `CTX-xx`、`USER`、`LIVE` 或 `-`，定义见 README |
| `能力/边界` | `F1`–`F4` 与正交 `B-*`，定义见能力边界 |

## 3. 分档定义

### 复杂度

- `C1`：单一、边界清楚、低歧义，通常一个产物或一次查询；
- `C2`：有少量约束或两三个步骤，需要简单核验；
- `C3`：多来源、多步骤或有明确验收门；
- `C4`：跨系统、跨角色、显著风险或多日协作；
- `C5`：战略性、高歧义、多阶段、多产物和多个人工拍板点。

### 首个可审阅结果时延

- `D0`：预计 30 分钟内到达首个可审阅结果；
- `D1`：同一工作日；
- `D2`：2–7 天；
- `D3`：2–6 周的实际执行才出现，不因“写一份十二周计划”而升档；
- `D4`：系统需要持续运行，不能用一次性方案冒充。

### 现实周期

- `H0`：一次性请求，没有显式现实时间跨度；
- `H1`：一天到一周；
- `H2`：2–6 周；
- `H3`：有界数月到多年；
- `H4`：周期性或持续工作。

`D` 衡量系统何时能给首个结果，`H` 衡量用户所管理的未来现实跨度。十二周转岗计划可以是 `D1 H3`；要求未来十二周每周跟踪、重排和提醒才可能是 `D4 H4`。输入数据覆盖的历史统计窗口、已经结束的绩效周期或被读取系统自身的更新周期，不会自动抬高 `H`。

### 交互轮次

- `R1`：1–2 轮确认；
- `R2`：3–4 轮采访或修订；
- `R3`：5–9 轮，通常含样稿/原型/证据反馈；
- `R4`：10 轮以上或多会话续接。

### 工具深度

- `K0`：不调用外部工具，只需对话推理或已有记忆；
- `K1`：1 个工具族；
- `K2`：2–3 个工具族；
- `K3`：4–5 个工具族；
- `K4`：6 个以上确实必需的工具族或跨组织系统编排。

`K` 从去重后的工具列机械派生，不允许先定 K 再补工具。预注入的 `CTX` 不计作工具；只有运行中要检索材料时才列 `rag`。

### 风险

沿用 SayDo 的 `S0`–`S3` 效果风险。标签按题面预计的最高效果计算，不按工具名字计算。`S3` 只表示潜在请求含不可逆或外部影响动作，不表示语音可批准。

## 4. 概率与领域配额

领域权重体现三点：SayDo 当前 coding 主线更成熟；写作、调研、项目协作是高邻接需求；生活生产力需要实质覆盖但不应淹没产品主场。配额是设计选择，不是市场事实。

H/M/L 的判断问题固定为：“合格目标人群在未来 12 个月主动提出这类请求的相对可能性有多高？”编写与复审时按目标人群覆盖、触发频次、自然表达可能性和罕见事件惩罚做领域内人工全局校准，再满足本表配额。构建器保留人工分档并断言配额，还锁住若干经复审确认的相对顺序；它不计算伪精确 demand score，也不用稳定 ID hash、C/D/H/R/K/S/F 或题面长度替语义判断。分层后再检查每个频率档都跨越多种复杂度、轮次、工具和风险，避免把“难”机械等同于“少见”。完整校准规则见 `03-频率与语义校准.md`。

## 5. 场景构造原则

1. 同一动作只有在输入、决策、产出、验收或外部 effect 至少两项不同的情况下才作为另一条；只换角色不算新情境；
2. 高频条目优先用用户会自然说出的短句，长尾与高复杂度条目才承载更多限定；
3. 同时覆盖新项目、已有项目新会话、续接会话、改需求、问状态、验收、重试和周期性巡检；
4. 同时覆盖 Quick、Guided、Explore 三种对话车道，以及直达验收和逐步确认两种执行模式；
5. 工具标签表达任务真实需要，不为了凑数强塞工具；
6. 高风险领域同时保留安全辅助和少量隐式/显式越权边界题；安全辅助不因题材敏感就标 `F4` 或 `S3`；
7. 所有上下文均为合成数据，不含真实凭据、客户隐私、个人联系方式或可执行的高风险指令；
8. 生活场景只收生产力问题，如预算、搬家、就医准备、家庭排班，不含娱乐消费或陪伴聊天。

## 6. RAG 包设计

16 个上下文包故意包含不同来源形态：正式 brief、会议纪要、用户反馈、日志摘录、表格摘要、旧版本说明、相互冲突的陈述和带日期的事实。每个 `manifest.md` 以 `as_of`、`valid_until`、按 claim scope 的权威规则和 `supported_questions` 白名单明确使用边界，用于测试：

- 是否先读 manifest，而不是把所有片段等权拼接；
- 是否能区分用户陈述、组织政策、外部材料和模型推断；
- 是否对旧数据、新数据和冲突结论保留不确定性；
- 是否在输出中给出可回查的来源，而不是把检索结果写成无来源事实。

每个 manifest 的 `required claims` 表把白名单进一步收紧为逐题合同：172 条合同逐题说明 50 个冻结来源文件实际支持的题目相关事实；若问题还标 `USER` 或 `LIVE`，表中必须同时声明待补的实体、字段、现势或权限。题面给出的临时日期、时长或会议条件若未出现在来源中，必须保留为题面条件并由 `USER` 归因，不能混入 fixture claim。构建器必须为每题提供显式合同，不生成包级通用兜底；验证器检查题目集合、来源文件、合同摘要和补充输入对称，避免“manifest 说支持，但材料其实答不了”的假闭合。

465 条含 `LIVE` 的记录另由 `contracts/live/*.json` 逐题登记，共 986 个对象来源。每个对象至少记录 `source_kind`、具体 locator 或 USER 提供的 connector locator、题面所需字段、单一相称 reader、权威、刷新要求、`as_of` 和授权主体/最小范围；一题有多个现势对象时逐对象分行，不用工具白名单或包级模板兜底。构建器把这些显式来源与 46 条最终 `F1` 能力合同稳定渲染到 `04-live-source-contracts.md`，验证器要求 LIVE/F1 集合、题面摘要、工具、CTX supplemental 和生成行严格对称。

## 7. 可判定验收标准

1. 固定 12 个 `questions/*.md` 文件中恰好 600 条记录，12 个前缀配额和 H/M/L 配额与上表完全一致；
2. ID 和规范化问题文本无精确重复；
3. 每条九个字段均非空，档位严格含 `C/D/H/R/K/S` 六个标签；
4. `C1`–`C5`、`D0`–`D4`、`H0`–`H4`、`R1`–`R4`、`K0`–`K4`、`S0`–`S3`、`F1`–`F4` 全部出现；
5. 工具数量与 K 档一致，所有工具词来自登记词表；46 条最终 `F1` 只允许显式登记的缺省 coding/workspace 用例，465 条 `LIVE` 与逐对象来源合同严格一一对应且没有空 locator、generic fallback 或 reader 错配；
6. 所有 `CTX-xx` 引用存在、在 manifest 的支持白名单中；16 个 manifest 完整登记 50 个来源文件，172 条逐题 required claims 指向真实文件、拒绝 generic fallback，并与 `USER`/`LIVE` 补充输入对称；题面临时条件不得冒充 fixture claim；
7. H/M/L 与 C/R/K/S 不得出现确定映射；验证器输出交叉表、核对高低频语义锚点并设置反耦合门；
8. 问题文件不含娱乐类主题、占位符或空泛的“做一下”，600 条执行 179700 对全量近重复扫描，候选仍须人工裁决；
9. 两路独立语义评审分别检查“领域/人群/自然度”和“能力/工具/风险/RAG”，再做一次独立 Codex 对抗审查；
10. 回修后通过 `node research/customer-question-corpus/validate.mjs`、临时副本类别 mutation 与语料范围 emoji 门禁；点名行和 manifest 的精确基线必须覆盖本轮修订，正式树在 mutation 前后摘要一致。全仓门禁若被范围外改动阻断，必须单独如实报告。
