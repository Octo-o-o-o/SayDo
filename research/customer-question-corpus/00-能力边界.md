# 00 · 能力边界

## 1. 提炼依据

本语料以 `docs/01-vision-and-problem.md`、`docs/02-product-definition.md`、`docs/03-architecture.md`、`docs/04-key-mechanisms.md`、`docs/05-roadmap.md`、`docs/09-data-contracts.md`、`docs/10-voice-ux-spec.md`、`docs/11-ui-spec.md`、`docs/modules/`、`docs/plan/IMPLEMENTATION-PLAN-2.md` 与 `HANDOFF.md` 为主要依据。能力状态以 2026-08-25 工作区实际文档现势为准；历史文档中较早的 P0/P1/P2 表述若与 `HANDOFF.md` 或当前排产源冲突，不作为现时能力断言。

## 2. 当前核心能力

以下能力已经有当前启用的代码路径与现场或自动化证据支撑，适合标为 `F1`。仅有 canonical 合同、候选实现或路线图排期不能单独升级为 `F1`：

- 以语音或控制台围绕本地项目持续对话，锚定项目、保存转写并续接会话；
- 读取本地项目，建立 M1 项目知识底座，按来源写 candidate/trusted 记忆，并用 FTS5 检索；
- 采访式澄清、类型化就绪清单、复述确认、独立就绪评估与决策包；
- 缺省启用的 `coding` 主线，经 Tier1 的 Cursor adapter 派发本地 agent，保留运行状态、证据和恢复信息；
- worktree 隔离、登记 verify、风险 S0–S3、S2 审批、S3 本机强认证或人工合并；
- 状态查询、中途改需求、取消、重试、结果分层摘要、diff/日志/产物上屏；
- settle 后语音、桌面通知或 ntfy 回叫，带免打扰、去重和确认状态；
- Dashboard、任务、审批、产物、记忆、成本、设置与 Focus/obligation 等控制面；
- macOS、Windows、Linux 桌面服务的分发候选与前台运行能力；常驻安装和系统通知仍存在平台差异。

## 3. 当前可做但需要条件或人工配合

下列场景标为 `F2` 更诚实：

- 需要浏览网页、读取 PDF、操作表格、制作演示稿、发邮件、使用日历或 SaaS 的任务：执行 agent 可在获得对应工具、登录态和授权后完成，但 SayDo 目前没有一套已验证的通用原生 connector 层；
- 涉及实时外部信息的研究：必须显式联网、留来源快照并处理新鲜度，不能只靠项目记忆；
- 手机浏览器经 Tailscale/LAN 查看控制台和接收 ntfy：薄版代码存在，但真机烟测与原生回叫形态没有全部关门；
- Claude Code CLI 生产主流程已有候选实现，但最终 live conformance 仍属收口项；
- `writing` 窄版合同与实现已存在，但缺省类型门关闭；只有显式开启、依赖齐备且逐节人工验收时才可执行；
- Hopper/Codex 有 bridge、合同或路线设计，但当前用户派发 route 仍固定为 Tier1，不能当作已接线执行路径；
- S3 WebAuthn 合并链自动化已覆盖，真人过卡仍需现场验证；
- 长任务可后台运行到验收点，但任意多步、跨长时、完全无人值守的可靠 workflow 仍不能承诺。

工具、connector、登录态和用户批准只说明外部系统的前置条件可能具备，不会自动把任意 `S3` effect 升为 `F2`。当前 canonical 的直接签发与消费路径没有覆盖流量切换、跨渠道发布、预订或购买、外发 RFP、自动通知或分派、发送邮件、支付等 effect；题面若仍要求 SayDo 在批准后直接执行这些动作，应标为 `F3` 实验需求或 `F4` 安全边界，不能仅因已有工具或登录态标成 `F2`。只有对应 effect 的判别合同、签发、消费和反例门都接通并验证后，才能重新评估其能力档。

## 4. 路线图能力

以下需求真实且值得采样，但应标 `F3`：

- `research`、`marketing`、`general` 的正式执行器合同与全量类型化验收；
- `planning` 的深度采访、文档体系、协同审阅、拆任务和批量派单全流程；
- 多任务并行的共享黑板、回叫聚合和一句话拆多任务；
- iOS/Android 原生外壳、PushKit/CallKit 来电式回叫、电话回叫；
- T3 服务端执行、remote repo、原生外部 app connector、主动巡检完整版；
- 引用级写作验证、parentProjectId/lineage 全量、记忆自动 consolidation；
- 可靠的跨天 workflow、原生 live steer 和复杂步骤循环；
- 多人会议旁听的合规、说话人、授权与私密分层产品化。

## 5. 明确边界

以下问题仍可作为潜在客户边界测试，但必须标 `F4`，且不应由系统冒充可自主完成：

- 娱乐陪伴、放歌、游戏、纯闲聊等非生产力用途，本语料完全排除；
- 诊断疾病、替代医生，作出法律结论或投资决策等高风险专业判断；
- 未经认证直接转账、下单、部署、删数据、对外发布、替用户签署合同；
- 用语音绕过 S3 强认证，或把会议中的泛化同意当作 owner 授权；
- 默认常听、后台监听环境，或声称能区分所有说话人；
- 承诺任意复杂工作都能隔夜自动交付，或把 `ready_for_review` 说成已经交付。

## 6. 能力匹配与边界标签

| 标签 | 含义 | 语料中的预期行为 |
|---|---|---|
| `F1` | 当前核心能力 | 在缺省启用的 coding 类型、可用 Cursor adapter、workspace、Gate 0 与 verify 条件满足时，可进入受治理执行闭环 |
| `F2` | 条件可做 | 先核对工具、登录态、网络、数据授权和人工检查点 |
| `F3` | 路线图需求 | 识别需求并诚实说明当前缺口，可先产出计划或人工协作版本 |
| `F4` | 产品或安全边界 | 拒绝越权部分，提供安全的资料整理、准备或人工决策辅助 |

`F` 只回答执行成熟度，不再用“题目涉及医疗、法律或财务”替代能力判断。每条另带一个正交边界标签：

语料中的最终 46 条 `F1` 由 `contracts/f1-capability-contracts.json` 逐题锁定，只覆盖当前缺省 coding/workspace 闭环，不因题面出现 `repo`、`test` 或 `shell` 就自动推导。每份合同同时登记题面摘要、workspace locator、允许工具与 effect、验证方法、证据和排除范围；`ENG-091` 与 `PRJ-025` 因需外部客户或账户 connector，明确登记为复核后降至 `F2`。隔离环境中的系统恢复顺序、备份可信度、灾备或生产切换仍需额外环境、权限和人工指挥，应标 `F2` 或更低成熟度；只有收窄为当前工作区内已经验证的 coding 动作才可进入 `F1`。

| 标签 | 含义 |
|---|---|
| `B0` | 无额外专业或授权边界 |
| `B-MED` | 医疗事实、诊断或用药边界 |
| `B-LEG` | 法律结论、权利义务或监管责任边界 |
| `B-FIN` | 税务、投资、付款或其他财务判断边界 |
| `B-PRIV` | 隐私、敏感资料或最小披露边界 |
| `B-ID` | 身份、冒充、联系人来源或凭据边界 |
| `B-ATTR` | 作者归属、署名或人格化代写边界 |
| `B-AUTH` | 发送、发布、部署、删除、签署、下单或客户承诺的授权边界 |

例如，整理症状时间线但不诊断是 `F2/B-MED`；自动替用户改药是 `F4/B-MED`。起草合同差异是 `F2/B-LEG`；替律师作最终法律结论才进入拒绝型边界。
