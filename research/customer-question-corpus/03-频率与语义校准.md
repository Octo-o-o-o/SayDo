# 03 · 频率与语义校准

本文件记录 600 条语料的可维护判断规则。它的作用不是把专家判断伪装成统计事实，而是让下一轮访谈、遥测或增补场景明确知道哪些假设应被推翻、哪些标签需要一起复核。

## 1. 频率先验的判断对象

每条只回答同一个问题：合格目标人群在未来 12 个月主动向 SayDo 提出这类请求的相对可能性有多高？

- `H`：目标人群广、触发反复出现、用户容易自然说出口；
- `M`：目标人群或触发条件较窄，但在一年内仍有现实机会出现；
- `L`：依赖罕见事件、重大转型、特殊监管情境或高度成熟的自动化委托。

这里的“合格目标人群”按领域变化。例如慢查询排障只在工程人群中比较，家庭复诊准备只在有照护责任的人群中比较。它不是把所有人口放入一个绝对概率分母。

## 2. 判断因子与反例

领域内人工校准同时考虑四类正向信号，不把它们相加成伪精确分数：

1. 目标人群覆盖：该角色在目标客户中是否常见；
2. 触发频次：任务是每日、每周、每月反复发生，还是一次性事件；
3. 表达可能性：用户是否会把它作为一个自然请求提出，而非只有产品专家才会构造；
4. 即时摩擦：当前痛点是否足以让用户当场寻求帮助。

罕见事件与特殊前提会降低先验，例如并购、跨国迁移、全公司重组、重大灾害、形式化验证、完全托管和跨多年转型。题面长度不能替代语义判断；长句既可能是罕见战略委托，也可能只是一个常见任务写得不自然。

高低频锚点用于防止整体漂移。例如日常 bug 排查、周报压缩、日程冲突和订阅续费应高于跨国重组、并购尽调、全球品牌迁移和家庭行政完全托管。验证器锁住一组明确锚点；独立评审仍需检查锚点之外的相对位置。

## 3. 为什么不按复杂度分层抽样

复杂任务可以高频，简单任务也可以长尾。若先在 C1–C5 内各自切 H/M/L，会把“同一复杂度中的相对常见”误写成全领域高频，导致罕见战略请求进入 H、日常复杂请求掉到 L。

当前方法是在每个领域内人工比较并校准到固定配额，再检查：

- H/M/L 各自至少覆盖四个复杂度档；
- 每档跨越多种轮次、工具深度和风险；
- 高频并不只等于短句、低工具或低风险；
- 长尾也包含少量简单但罕见的请求。

配额仍是设计约束。拿到真实信号后，应先保存旧先验与证据日期，再用访谈提及率、实际请求率、任务复发率和目标客户覆盖更新，不做事后解释。

## 4. 口语自然度与可评测性

问题文本保留潜在客户会说的省略、指代、反问、上下文续接和安全约束；目的、验收与边界放在独立字段，不要求每句话都把完整 oracle 背出来。高频条目优先短而直接，长尾条目允许带更多前提。

同时守住三条下限：

- 不能为追求口语而删掉会改变授权或安全等级的条件；
- 不能把两个只有角色不同的同构请求算作不同场景；
- 不能用空泛的“帮我做一下”换取短句，至少要能判断主产物或下一步。

验证器检查精确重复、全量两两近重复、问句比例、固定句式集中度和长度分布；人工评审负责判断真实感、同构场景与领域边界。

## 5. 工具、输入和上下文闭合

三类概念必须分开：

- 工具：运行时需要调用的能力，例如 `repo`、`browser`、`calendar`、`crm`；
- 输入模式：事实从哪里来，包括自包含、`CTX`、`USER`、`LIVE`；
- RAG：运行时要在输入集合内检索，不等同于“已有一个 CTX 包”。

工具列只登记完成题目确需的唯一工具族，K 档从去重数量派生。每条 `LIVE` 的每个现势对象都必须在 `contracts/live/*.json` 登记 source kind、具体 locator、题面所需字段、单一相称 reader、权威、新鲜度、`as_of` 与授权主体/最小范围；465 条 LIVE 与合同集合必须全等，不能有 generic fallback。`CTX+LIVE` 还必须让 manifest supplemental 与逐题 LIVE 合同完全一致。纯编排/输出工具不能单独闭合 LIVE，`rag`、`document`、`pdf` 也不能成为任意现势任务的万能 reader。用户附件、手工表、原计划等不能因为已有相似 fixture 就省略 `USER`；冻结网页摘要不能冒充当前法规、价格或竞争态势。所有 `D4` 条目还必须包含与题意相称的持续调度、状态或监控工具。

每个 CTX manifest 的 required claims 表将题目需要的事实绑定到具体来源文件。172 条合同必须逐题陈述 fixture 实际支持的事实，并明确仍需 `USER` 或 `LIVE` 补齐的实体、字段、现势或权限；不接受把题目目的拼成事实或用包级 generic fallback。题面临时给出的日期、时长或场合若不在来源中，只能作为题面条件并由 `USER` 补充，不能捏造成 fixture claim。验证器检查：问题引用、白名单、required claims 摘要、50 个来源文件、有效期和补充输入全部对称。

## 6. 风险、能力与专业边界

`S` 回答“题面预计产生的最高现实 effect 是什么”，`F` 回答“SayDo 应如何匹配这类请求”，`B` 回答“哪类专业、隐私、身份或授权边界必须守住”。三者不能互相替代。

- 读敏感材料不一定是 S3，但不能误标成 S0；
- 写代码或修改外部 SaaS 状态至少需要与实际 effect 相称的风险；
- 发送、支付、提交、部署等真实外部 effect 必须停在相应确认门；
- 生产数据库、schema、双写或回填不得低于 S2，企业敏感数据也不得保留 S0；
- 真实圈外写入必须说明预览、确认对象和授权边界，高金额法律或财务任务不得使用 B0；
- 安全整理医疗、法律或财务材料可以是 F2，越权诊断、代签、自动交易或明确绕过确认才是 F4；
- 一条记录只有一个主边界，跨域协调题按主要输出选择，其他限制写进问题和目的。
- 最终 46 条 `F1` 使用逐题 capability contract，明确当前缺省 coding/workspace 基线、workspace locator、允许工具与 effect、验证证据和排除范围；系统级恢复、备份、区域切换或外部 connector 任务不能因前缀或工具形状相似而自动进入 `F1`。

规则匹配只能抓明显反例，不能替代逐条语义判断。每次批量改写后，都要重新审查 S0、S3、F1、F4、K0、K4 以及所有仅依赖 CTX 的条目。

## 7. 维护顺序

1. 先在 `rebuild.mjs` 修改人工覆盖、标签规则或上下文事实合同；
2. 执行构建，并用故障注入确认可捕获的晋升失败会恢复现有问题与 manifest；断电或进程强杀不在该保证内；
3. 执行 `validate.mjs`，检查总量、配额、交叉表、风险、465 条逐对象 LIVE 合同、46 条 F1 capability contract、生成式 04 交付和上下文闭合；
4. 对 S0/S3、F1/F4、K0/K4、CTX-only 与频率锚点做全量语义复核；
5. 执行两路独立评审和一次外部对抗审查；
6. 对频率、F1、纯 LIVE、CTX+LIVE、USER 归因、敏感边界、时域、effect 和自然度分别在临时副本注入反例，确认 validator 非零退出且正式树摘要不变；
7. 修复发现后用全新上下文复审，并记录证据与未解决限制。

只有步骤 1–7 都完成，才可以把本轮称为“语料构建和检查都跑完”；它仍不等于完成市场验证、证明任意来源语义蕴含或完成真实执行 benchmark。
