# 模拟用户使用数据计划

## 1. 目标与边界

主问题集固定为 600 条，不再通过追加近义单句扩大规模。本目录从其中选取 72 条代表性问题，补成可供访谈演练、对话设计、提示词回放和人工评测使用的多轮模拟会话。

模拟数据回答的是“用户接下来会怎么补信息，系统应该如何澄清、读取材料、停在审批点并从失败中恢复”，不是证明真实 connector 已登录、外部 effect 已接通或市场概率已经验证。

以下内容不进入本轮硬验收：

- 真实 SaaS 账号、object ID、token 或可执行 locator；
- 逐字一致的理想助手答案；
- 对全部 600 条生成完整 transcript；
- 用模拟频次替代客户访谈、遥测或市场研究。

## 2. 样本规模与分层

固定 72 个会话，每个领域 6 个。领域内频率按下列方式选择，合计保持 H 32、M 25、L 15：

| 领域组 | 领域 | 每域 H/M/L |
|---|---|---|
| 核心工作场景 | ENG、PRJ、WRT、RES、OPS、SAL、MKT、DAT | 3/2/1 |
| 个人成长与生活 | LRN、LIF、FAM | 2/2/2 |
| 职业与自由职业 | CAR | 2/3/1 |

选择时同时满足：

- C1–C2、C3、C4–C5 均有样本；
- R1–R4、D0–D4、H0–H4、K0–K4、S0–S3、F1–F4 均至少出现一次；
- `-`、`USER`、`CTX`、`LIVE` 及组合模式均有样本；
- 至少 12 个会话包含 S3 或 F4 边界，测试拒绝、降级或写前确认；
- 至少 18 个会话使用现有 CTX fixture；至少 18 个要求 USER 补材料；至少 24 个包含 mock LIVE 工具结果；
- 至少 8 个生活/家庭场景，且不含娱乐。

## 3. 会话类型

72 个会话分散覆盖以下生命周期，不要求每类互斥：

| 类型 | 最低数量 | 观察点 |
|---|---:|---|
| 首次请求与最小澄清 | 18 | 只问会改变产出或安全路径的问题 |
| 用户补附件或口述条件 | 14 | USER 输入与 fixture 事实分开 |
| RAG 冲突与时效 | 12 | authority、日期、未知项和来源引用 |
| LIVE 查询与工具降级 | 16 | 登录态/数据缺失时 fail-closed，不伪造结果 |
| 写前确认与授权 | 12 | 对象、内容、渠道、影响范围、回滚点 |
| 中途改需求或拒绝草稿 | 8 | 不沿用已撤回约束，保留决策记录 |
| 工具失败、空结果或脏数据 | 10 | 解释失败证据并给安全替代路径 |
| 暂停、续接与状态查询 | 8 | 复述已确认事实、当前状态和仍待输入 |
| 明确越权请求 | 6 | 拒绝危险部分，提供可接受的降级帮助 |

## 4. 单个会话结构

每个会话必须包含：

1. `SIM` ID 与对应 corpus ID；
2. 原始标签摘要和选样理由；
3. 回放前状态：已注入 CTX、USER 材料、mock LIVE 数据、授权状态；
4. 至少 3 个用户轮次，其中一轮体现补充、纠正、改需求、确认或拒绝；
5. 每轮的“期望系统动作”，描述行为而非强制逐字答案；
6. 至少一个 mock 工具/RAG 事件，或明确说明 K0 为什么不需要工具；
7. 首个可审阅结果；
8. `必须做到`、`不得做`、`可接受差异`三类 oracle；
9. 一个失败或扰动变体，以及期望恢复行为；
10. 最终状态：等待用户、ready_for_review、拒绝高风险部分或已给草稿。不得把 `ready_for_review` 写成完成。

## 5. Fixture 设计

- 复用现有 `contexts/CTX-xx` 时只引用 manifest 白名单内事实；
- mock LIVE 数据全部为合成快照，按 SIM ID 放在 `fixtures/`，不得包含真实公司、个人联系方式、凭据或可执行支付/发布信息；
- fixture 可以模拟 `ok`、`empty`、`stale`、`conflict`、`permission_denied`、`partial` 六种结果；
- 模拟 locator 只用于把会话与本地 fixture 对上，不宣称是真实 connector 地址；
- 涉及 S3 时只提供预览、挑战或拒绝结果，不伪造正式授权收据和真实外部消费。

## 6. 适度验收标准

### A 级硬门

- 会话不是 72 个、不是每域 6 个，或引用不存在/重复的 corpus ID；
- H/M/L 不是 32/25/15，或主要标签/原问题与源记录不一致；
- 缺少要求的用户轮次、oracle、失败变体或 fixture；
- fixture 与现有 CTX source 明确矛盾，或把 USER/LIVE 条件冒充冻结事实；
- S3/F4 会话直接执行、伪造授权/回执，或泄露敏感原文；
- 含娱乐场景、真实凭据、个人联系方式或不可安全分发的数据；
- 生成器/验证器不能重复运行，或生成结果不稳定。

### B 级改进项

- 个别句子偏书面、轮次略长、工具选择存在可解释替代；
- 标签存在合理的相邻档争议；
- mock 数值还可更贴近某行业，但不影响行为测试；
- oracle 可以更细，但当前已能判定核心成功与禁止动作。

B 级不阻断交付，集中记录并择要修复；C 级只作为后续真实访谈和执行 benchmark 的增强建议。

## 7. 门禁命令

实施结束至少运行：

```bash
node research/customer-question-corpus/simulations/validate-simulations.mjs
node research/customer-question-corpus/simulations/test-simulation-mutations.mjs
find research/customer-question-corpus/simulations -type f -print0 \
  | xargs -0 bash scripts/check-emoji.sh
```

验证器应输出 72 个会话、12 个领域、H/M/L 32/25/15、标签覆盖、输入模式覆盖、生命周期覆盖、fixture 数量、所有引用 ID 存在，以及 A 级错误为 0。独立评审只把 A 级作为返工阻断；B/C 写入报告，不启动无限复审循环。
